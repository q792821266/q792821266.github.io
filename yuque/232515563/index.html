分布式事务

分布式事务指在分布式系统中，多个服务和数据库之间需要保持数据一致性的事务操作。由于分布式系统的复杂性，实现一致性具有挑战性。以下是几种主流的分布式事务解决方案。

简介

方案没有孰优孰劣，只有适用场景的不同。理解CAP（Consistency, Availability, Partition tolerance）的原理对分布式事务的设计会有一定的帮助。

两阶段提交（2PC，Two-Phase Commit）

2PC的设计原则就是强一致性

原理：

  • 第一阶段，准备：协调者向所有参与者发送准备请求，参与者执行事务但不提交，返回是否可以提交
  • 第二阶段，提交：如果所有参与者都返回”可以提交“，协调者发送提交请求，参与者提交；否则发送回滚请求

优点:

  • 实现简单，强一致

缺点：

  • 同步阻塞，性能差
  • 协调者单点故障风险高
  • 不适合高并发场景
三阶段提交（3PC， Three-Phase Commit）

3PC通过引入超时与预提交，弱化了一致性以提升可用性，增加容错。这是一种性能和一致的平衡。

原理：

在2PC基础上增加一个”预提交“阶段，降低阻塞和协调者宕机的风险。在每个阶段，参与者都可以通过超时机制自行决定回滚事务。协调者宕机，参与者不会无限等待，而是更具预设的超时机制自动回滚，避免资源长时间锁定

  • Can Commit：询问是否可以提交
  • Pre Commit：预提交，锁定资源但不真正提交
  • Do Commit：正式提交或回滚

优点：

  • 对协调者容错性更高

缺点：

  • 实现复杂，仍然存在性能瓶颈
本地事务+消息队列（异步确保最终一致性）

原理：

  • 服务A完成本地事务后，发送消息到消息队列
  • 服务B从队列中消费消息，执行自己的事务

优点：

  • 高性能，解耦
  • 最终一致性

缺点：

  • 实现复杂，需要处理消息幂等性、重复消费的问题
TCC（Try-Confirm-Cancel）模式

原理：

  • Try：预留资源
  • Confirm：确认并执行操作
  • Cancel：取消并释放资源

优点：

  • 灵活控制事务流程
  • 支持业务定制

缺点：

  • 每个服务都需要实现三种操作，开发成本高

实现：

  • 使用TCC框架，如ByteTCC 、Hmily
  • 每个服务需要实现三种接口，配合事务协调器
Saga模式

原理：

将长事务拆分为多个本地事务，每个本地事务都由对应的补偿操作（回滚）

优点：

  • 非阻塞，适合长事务 微服务架构
  • 支持最终一致性

缺点：

  • 需要设计补偿逻辑，业务侵入性强

实现：

  • 使用Saga框架，如Apache ServiceComb Saga 、Seata
  • 结合Spring Cloud微服务架构
分布式数据库自带事务机制

如Google Spanner 、TiDB、 CockroachDB等数据库支持分布式事务

优点：

  • 开发简单，数据库层面保证一致性

缺点：

  • 以来特定数据库，迁移成本高

如何选择

  • 强一致性：考虑2PC 或 TCC
  • 高性能、可接受最终一致性：考虑消息队列或Saga
  • 业务复杂度高：Saga
  • 如果使用分布式数据库：可直接使用数据库事务

一些思考

  1. 3PC 引入了超时机制，为什么2PC不引入呢？
    确实2PC可以引入超时机制，但是这会导致一致性风险。
  • 如果参与者在超时后回滚，而协调者其实已经决定提交但是消息未送达，这会导致部分提交，部分回滚，破坏一致性。
  • 2PC的设计假设协调者是”最终裁决者“，参与者不能自行决定事务结果，否则违背了协议的核心原则强一致性
  • 2PC：倾向于 Consistency + Partition Tolerance，牺牲 Availability
  • 3PC：尝试在 Consistency 和 Availability 之间做平衡，但在网络分区下可能牺牲一致性

  1. 3PC阶段中Can Commit的意义是什么

  2. 提前探测参与者状态

  • 协调者先询问参与者是否可以提交，而不是直接要求准备提交
  • 参与者此时没有锁定资源，只是做出判断。这样是非侵入的，不会影响参与者的状态。也可以提高成功率，如果有参与者拒绝，可以提前放弃，避免后续的锁定
  1. 为后续做准备
  2. 增强容错
  • 即使协调者在这个阶段宕机，参与者此时并没有做任何操作，不会造成资源锁定，使整个协议更具有可恢复性
  1. 因为引入了新的阶段，或者说从2阶段变成了3阶段，阶段之间的切换变多，就可能在此期间出现一致性问题，比如Can commit资源可用，但是Pre Commit就不可用了

确实会出现这种不一致问题，但是

3PC的设计意图是：降低阻塞和提高容错性，而非完全避免资源不一致。

✅ 总结建议

协议 Spring Boot 实现方式 推荐场景
2PC Atomikos + XA 数据源 强一致性，事务短
3PC 自定义协调器模拟 理论研究或容错测试
TCC Hmily 框架 高性能业务，资源预留明确

分布式事务方案对比表

协议 核心机制 一致性类型 优点 缺点 Spring Boot 实现方式
2PC 两阶段：Prepare → Commit/Rollback 强一致性 简单直观，事务原子性强 阻塞严重，协调者单点故障 使用 XA 数据源（如 Atomikos）
3PC 三阶段：CanCommit → PreCommit → Commit/Rollback 弱一致性 非阻塞，容错性更好 实现复杂，工业界少用 自定义协调器模拟流程
TCC Try → Confirm → Cancel，业务级资源预留 强一致性 灵活，适合资源控制场景 业务侵入性强，开发成本高 使用 Hmily 框架，注解式 TCC
Saga 本地事务 + 补偿机制，状态机驱动 最终一致性 非阻塞，适合长事务 补偿逻辑复杂，一致性弱化 使用 Seata Saga 状态机定义
分布式与中间件 > 事务与一致性
