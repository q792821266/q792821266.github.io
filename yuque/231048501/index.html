LDAP

🧠 LADP是什么？为什么出现？

✅ 定义

LDAP（Lightweight Directory Access Protocol）是一种用于访问和管理目录服务的协议。目录服务是一种专门优化用于读取的数据库，常用于存储用户、组织、设备等信息

✅ 出现的背景

在企业种，随着用户数量和系统复杂度的增加，传统的数据库或文件系统难以高效管理用户身份信息。LDAP作为一种轻量级协议，提供了：

  • 高效的读取性能
  • 层级结构（类似文件系统）
  • 标准化的身份管理方式

它最初由X.500标准演化而来，成为企业身份管理的核心技术之一

🔐LDAP的身份验证与权限控制机制

身份验证（Authentication）

LDAP的身份验证通常通过以下方式实现：

  • 简单绑定（Simple Bind）：客户端提供用户名（DN）和密码，LDAP服务器验证
  • SASL绑定：支持更复杂的认证机制，如Kerberos
  • 在Spring Security中，通常使用userDnPatterns 来构造用户的DN，然后进行密码验证

权限控制（Authorization）

LDAP本身不直接控制权限，而是通过以下方式实现：

✅ 基于组（Group-Based Authorization）

  • 用户属性某个组（如 cn=admin ,ou =groups）
  • 应用根据用户所属组授予权限（如hasRole(“ADMIN”)）

✅ 基于属性（Attribute-Based Authorization）

  • 用户条目中包含角色属性
  • 应用读取属性并映射为权限

✅ 结合应用权限系统

  • LDAP只做身份验证
  • 权限控制由数据库或RBAC系统完成

🧰 LADP权限控制的细节

控制点 描述
DN（Distinguished Name） 唯一标识用户或组，如 uid=john,ou=people,dc=example,dc=com
Group Membership 用户条目中包含 memberOf
或组条目中包含 member
ACL（Access Control List） LDAP 服务器可配置访问控制策略，限制谁能读写哪些条目
Schema 定义哪些属性可用于权限控制，如 role
, department
, title

🧭 其他身份与权限校验方式

除了LDAP，还有下列现在身份校验与授权方式：

✅OAuth2.0 / OpenID Connect

  • 用于Web和移动应用的授权协议
  • 支持第三方登录，如Google，Github
  • 常用于微服务架构

✅SAML（Security Assertion Markup Language）

  • 企业级单点登录协议
  • 常用于与AD 、 SSO 系统集成

✅RBAC （Role-Based Access Control）

  • 基于角色的权限控制
  • 用户 -> 角色 -> 权限
  • 这种其实更常用于Web应用

✅ABAC （Attribute-Based Access Control）

  • 基于属性的权限控制
  • 更灵活，适合复杂场景

JWT

JWT（JSON Web Token）本质是一种令牌格式和传输机制，并不是一种完整的身份验证协议。它通常与OAuth2.0或OpenID Connect等协议配合使用，来完成身份验证和权限控制

JWT是什么

JWT是一种轻量级的令牌格式，具有以下特点：

  • 自包含：令牌中包含用户信息和权限声明（Claims）
  • 无状态：服务器不需要储存会话信息
  • 可签名：通过HMAC或RSA 签名保证令牌完整性

一个典型的JWT包含三部分：

JWT和OAuth2.0的关系

项目 描述
OAuth2.0 是一个授权协议，定义了如何获取访问令牌（access token），只负责授权
JWT 是一种令牌格式，可以作为 OAuth2.0 的 access token
OpenID Connect 是基于 OAuth2.0 的身份认证协议，使用 JWT 作为 ID Token，同时兼顾授权与认证

虽然 JWT 本身不是权限控制系统，但它可以携带权限信息，例如：

  • 用户角色（role）
  • 权限列表（scope）
  • 组织或部门信息（org）

这些信息可以被后端服务解析并用于授权判断。

如果你正在设计一个身份认证系统，可以根据场景选择：

  • 企业内部系统：LDAP + RBAC
  • 微服务架构：OAuth2.0 + JWT
  • 跨域登录：OpenID Connect + JWT

✅ SAML（Security Assertion Markup Language）基本流程

SAML 是一种 基于 XML 的身份认证协议，主要用于 SSO 场景，流程大致如下：

  1. 用户访问应用（Service Provider, SP）
    用户打开企业应用，应用发现用户未登录。
  2. 应用重定向到身份提供者（Identity Provider, IdP）
    SP 将用户重定向到 IdP（企业认证系统）。
  3. 用户在 IdP 登录
    用户输入账号密码，IdP完成身份验证。
  4. IdP 生成 SAML Assertion（XML 格式）
    这个 Assertion 包含用户身份信息（如用户名、邮箱），并签名保证安全。
  5. SP 验证 Assertion
    应用验证签名，确认用户身份，建立会话，实现 SSO。

特点：

  • 使用 XML 格式，基于浏览器重定向。
  • 主要用于 身份认证，不涉及细粒度权限（通常权限在应用端处理）。
  • 常用于企业内部系统集成（如与 AD、LDAP）。

✅ 1. 授权服务器如何认证身份？

  • 用户在 IdP（Identity Provider） 登录，输入账号密码。

  • IdP 验证用户凭证（通常对接 LDAP、AD 或数据库）。

  • 登录成功后，授权服务器生成：

  • ID Token（JWT格式）：用于身份认证，包含 sub（用户ID）、name、email 等。

  • Access Token：用于授权访问资源，包含 scope、audience、exp 等。

✅ 2. ID Token 的安全性

  • 格式：JWT（Header + Payload + Signature）。

  • 签名：

  • 使用授权服务器的 私钥（通常是 RSA 或 EC）。

  • 客户端或资源服务器使用 公钥验证签名。

  • 作用：证明“用户是谁”，用于 SSO。

✅ 3. Access Token 的安全性

  • 格式：可以是 JWT，也可以是 opaque（不透明字符串）。

  • 验证方式：

  • 如果是 JWT：

  • 客户端或资源服务器验证签名（使用授权服务器的公钥）。

  • 检查 exp（过期时间）、aud（目标服务）、scope（权限）。

  • 如果是 opaque：

  • 客户端调用授权服务器的 Token Introspection API 验证令牌有效性。

✅ 4. 客户端如何验证授权码（Authorization Code）？

  • 授权码是 OAuth 2.0 授权流程中的临时凭证，客户端不能直接验证它。

  • 正确做法：

  • 客户端拿授权码去授权服务器的 Token Endpoint 换取 Access Token 和 ID Token。

  • 授权码本身只在服务器端验证，客户端只负责安全传输。

✅ 安全要点

  • ID Token 和 Access Token 都必须签名，客户端验证签名。

  • 使用 短期有效期（如 5-15 分钟），并支持刷新令牌。

  • 使用 HTTPS 保证传输安全。

  • 客户端必须验证：

  • 签名是否正确。

  • exp 是否过期。

  • aud 是否匹配当前应用。

  • iss 是否是可信授权服务器。

✅ 一句话总结：
授权服务器认证身份 → 生成 ID Token（身份）+ Access Token（授权），客户端验证签名、过期时间、audience，确保令牌合法。

** 资源服务器验证 Access Token 后，是否需要再次调用授权服务器 **

答案取决于 Access Token 的类型：

✅** 两种常见情况**

  1. Access Token 是 JWT（自包含）

验证方式：

资源服务器使用授权服务器的 公钥 验证签名。
检查 exp（过期时间）、aud（目标服务）、scope（权限）。

权限校验：

如果 JWT 中包含 roles 或 scopes，资源服务器可以 直接根据这些信息做权限控制。

是否需要再次调用授权服务器？

不需要，因为 JWT 是自包含的，验证签名和字段即可。

✅** 企业最佳实践：
Access Token 使用 JWT，资源服务器本地验证签名 + 权限字段，避免额外网络调用，提高性能。**

  1. Access Token 是 Opaque（不透明字符串）

验证方式：

资源服务器无法解析 Token，只能调用授权服务器的 Token Introspection API。
授权服务器返回 Token 是否有效，以及用户信息、权限。

是否需要再次调用授权服务器？

需要，因为资源服务器无法自行验证。

✅** 这种方式常用于安全要求极高的场景，但性能较差。**

✅** 总结**

JWT Access Token → 本地验证签名 + 权限字段，性能高。
Opaque Access Token → 调用授权服务器验证，安全性高但性能差。

✅** 企业微服务最佳实践**

Gateway 或 IdP 发放 JWT Access Token（签名 + 短期有效期）。
资源服务器本地验证签名和权限字段，不再调用授权服务器。
如果权限复杂，可以：

JWT 中只放用户ID，资源服务器调用权限服务（不是授权服务器）。
或使用 API Gateway 做统一权限校验。
