过滤器和拦截器

过滤器和拦截器都是 Java Web 开发中用于请求处理的中间件，但它们在实现原理、作用范围、使用场景等方面存在显著差异。以下是两者的核心区别及适用场景总结：

⚙️ 一、核心区别对比

对比维度 过滤器（Filter） 拦截器（Interceptor）
实现原理 基于函数回调（FilterChain.doFilter()） 基于反射机制（动态代理/AOP）
依赖环境 依赖 Servlet 容器（如 Tomcat） 依赖 Web 框架（如 Spring MVC）拦截器可以依赖于Servlet容器，但更多依赖于Spring MVC框架
作用范围 对所有请求生效（包括静态资源） 仅对 Controller 请求生效（动态资源）
生命周期 随容器启动初始化一次，销毁时调用 destroy() 每个请求独立调用，可多次执行（如 preHandle）
访问上下文 仅能操作 ServletRequest/ServletResponse 对象 可访问 Controller 上下文（如值栈、ModelAndView）
注入能力 无法注入 Spring Bean（非 Spring 管理） 可注入 Spring Bean（如 Service 层业务逻辑）
执行顺序 在 Servlet 之前执行，由 web.xml 配置顺序决定 在 Controller 之前/后执行，顺序可通过 order 控制

⏱️ 二、执行流程差异

  1. 过滤器执行时机
    • 请求阶段：进入 Servlet 容器 → 过滤器 → Servlet
    • 响应阶段：Servlet 处理完成 → 过滤器 → 返回客户端
    • 示例：设置全局字符编码（request.setCharacterEncoding("UTF-8")）。
  2. 拦截器执行时机
    • preHandle：Controller 方法执行前（权限校验）
    • postHandle：Controller 执行后，视图渲染前（修改响应数据）
    • afterCompletion：视图渲染后（资源清理）
    • 示例：记录接口耗时（在 preHandle 记录开始时间，afterCompletion 计算时长）。

🛠️ 三、典型应用场景

过滤器的适用场景

• 全局请求处理：字符编码统一设置、响应压缩（GZIP）。

• 安全防护：SQL 注入过滤、XSS 攻击防御（过滤请求参数）。

• 静态资源控制：缓存策略（如 Cache-Control 头设置）。

拦截器的适用场景

• 业务逻辑拦截：登录状态验证（session 检查）、接口权限控制。

• 精细化日志：记录请求参数、响应结果、异常信息。

• 性能监控：统计接口耗时、QPS（结合 AOP 思想）。

⚠️ 四、关键注意事项

  1. 执行顺序冲突
    • 若同时配置过滤器和拦截器，过滤器始终优先执行（在 Servlet 层拦截）。
    • 多个拦截器按配置顺序执行，可通过 Order 注解调整。
  2. 性能影响
    • 过滤器处理所有请求（包括静态资源），过度使用可能影响性能。
    • 拦截器仅作用于 Controller 层，更适合业务相关操作。
  3. 错误处理
    • 过滤器可通过 response.sendRedirect() 跳转错误页。
    • 拦截器可直接抛出异常，由全局异常处理器捕获。

💎 总结：如何选择？

• 选过滤器：需处理所有请求（包括静态资源）、修改请求/响应原始数据（如编码、压缩）、安全过滤等底层操作。

• 选拦截器：需结合业务逻辑（如权限校验、日志记录）、访问 Spring 容器 Bean、精细化控制 Controller 方法。

实际项目中二者常结合使用：

  1. 过滤器处理全局安全与编码 → chain.doFilter() 传递请求；
  2. 拦截器实现业务层权限校验 → 调用 Service 验证用户角色。
    例如：用户登录场景中，过滤器校验 Token 格式 → 拦截器调用 UserService 验证 Token 有效性。

🛠️ 四、典型应用场景

过滤器适用场景

  1. 全局日志：记录所有请求的URL、耗时（如LoggingFilter）。
  2. 跨域处理：添加Access-Control-Allow-*响应头。
  3. 字符编码：统一设置request.setCharacterEncoding("UTF-8")。

拦截器适用场景

  1. 登录验证：检查Session或JWT令牌（如AuthInterceptor）。
  2. 性能监控：在preHandle()记录开始时间，在afterCompletion()计算耗时。
  3. 参数预处理：在preHandle()中校验参数合法性，非法时返回错误码。

⚠️ 五、避坑指南

  1. 避免循环调用
  • 在过滤器中调用chain.doFilter()，拦截器中preHandle()返回true，否则请求被阻塞。
  1. 生产环境安全
  • 禁用Swagger UI的Try it out功能，或通过网关（如Nginx）限制访问。
  1. 性能优化
  • 过滤器和拦截器中避免复杂数据库查询，将耗时逻辑移至Service层。

💎 总结

  • 过滤器：Servlet容器级组件，适合全局请求/响应处理（如日志、编码）。
  • 拦截器：Spring MVC框架级组件，适合控制器方法拦截（如权限、性能监控）。
  • 关键步骤：
  1. 实现接口（Filter / HandlerInterceptor）。
  2. 注册组件（FilterRegistrationBean / InterceptorRegistry）。
  3. 控制顺序（@Order或注册顺序）。

通过合理组合二者，可构建灵活且安全的请求处理管道。实际项目中，常见方案是：过滤器处理全局事务（如跨域） → 拦截器处理业务相关逻辑（如鉴权） → 控制器执行业务。

✅ 为什么记录请求响应推荐使用 Filter？

  1. 可以访问和包装响应体
    Spring 的 HandlerInterceptor 无法直接访问响应体（HttpServletResponse），而 Filter 可以通过 ContentCachingResponseWrapper 包装响应体并读取内容。
  2. 更早拦截请求
    Filter 在请求进入 Spring MVC 之前就能拦截，适合做统一日志记录、审计、跨域处理等。
  3. 适用于所有请求类型
    包括静态资源、错误页面等，而 Interceptor 只拦截控制器方法。
  4. 更容易与日志系统集成
    Filter 可以统一记录所有请求的入口和出口，便于与 ELK、Splunk 等日志平台对接。

📦 流（Stream）与可读性之间的关系

在 Java 的 Servlet API 中，响应体是通过 HttpServletResponse.getOutputStream() 或 getWriter() 写入的。这些方法返回的是 输出流（OutputStream），它的特点是：

  • 单向写入：你只能往里面写数据，不能从中读取已经写入的内容。
  • 不可回读：一旦数据被写入并刷新到客户端，就无法再从 HttpServletResponse 中获取这些数据。
  • 没有缓存机制：默认情况下，Servlet 不会自动缓存响应内容。

🧠 类比理解

你可以把原始的 HttpServletResponse 想象成一个 水龙头，你只能往外放水（写数据），但不能回收已经流出的水（读数据）。

而 ContentCachingResponseWrapper 就像在水龙头下放了一个 水盆，你可以在水流出之前先收集起来，之后再查看里面的水（响应内容）。

这里引申出一个问题， 我们这里说的流和Stream的那种流不是同一个概念。这里的流是写入的IO流， Stream流指的是数据流，数据流可以回溯，重复度，但是IO流不行。

🧩 为什么说“不是完全不能”？

如果你在 Interceptor 中提前包装响应对象（比如在 preHandle 中），然后在 afterCompletion 中读取缓存内容，是可以做到的。但这有几个前提：

1. 必须在 DispatcherServlet 之前包装响应对象

这通常需要在 Filter 中完成，因为 Interceptor 是在 DispatcherServlet 之后执行的，已经来不及包装。

2. 必须使用 ContentCachingResponseWrapper

Spring 提供的这个类可以缓存响应内容，但你必须确保：

  • 在请求开始时就用它包装 HttpServletResponse
  • 在响应完成前调用 getContentAsByteArray() 读取内容
  • 最后调用 copyBodyToResponse() 把内容写回客户端

3. 必须处理响应流的生命周期

如果你在 Interceptor 中读取响应体但没有正确写回，会导致客户端收到空响应或乱码。

✅ 最佳实践建议

  • Filter：负责包装请求和响应对象，记录原始 HTTP 数据
  • Interceptor：负责记录业务层信息，如方法参数、返回值、执行时间等

这种组合方式既能满足审计需求，又能保持代码清晰和高性能。

✅ 4. 处理异常场景

⚠️ 为什么不能用它来读取响应体？

因为此时响应体已经被写入 OutputStream，而 HttpServletResponse 没有缓存机制，也没有提供读取响应体的 API。除非你在更早的阶段（如 Filter）就用 ContentCachingResponseWrapper 包装了它，否则你在 Interceptor 中是无法访问响应内容的。

afterCompletion 中的 HttpServletResponse 是为了让你访问响应的元信息（如状态码、头部），而不是响应体内容。
如果你需要读取响应体，必须在 Filter 中包装响应对象。
