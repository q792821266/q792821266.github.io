传输协议（HTTP/TCP/TLS...）

区别

HTTP调用：

  1. 协议：基于HTTP协议，通常用于Web服务
  2. 通用：跨平台、跨语言，任何支持HTTP的客户端都可以于服务端通信
  3. 数据格式：使用JSON或XML进行数据传输，较臃肿
  4. 灵活性：HTTP调用不需要客户端和服务端使用相同的技术栈，只需要遵循RESTful规范

RPC调用

  1. 协议：基于TCP/IP协议，通常用于高性能服务调用
  2. 效率：RPC调用更高效，数据传输格式可以自定义，通常使用二进制格式（如Protobuf）减少数据开销
  3. 透明：RPC强调像调用本地服务一样调用远程服务，调用过程对用户透明
  4. 技术栈：要求客户端和服务端使用相同的RPC框架（如gRPC 、Dubbo），需要一致

如何选择？

如果对性能要求高，且可使用统一的技术栈，RPC是更好的选择。

如果需要跨平台、跨语言的调用 HTTP更合适。

RPC常见的实现

  • gRPC
    Google开发，支持多种编程语言，使用Http/2协议和Protobuf数据格式。高效、跨语言、支持双向流和连接复用
  • Thrift
    最初Facebook开发，现为Apache开源项目，支持25中编程语言。轻量、跨语言、支持多种序列化格式
  • Dubbo
    由阿里巴巴开发，主要用于Java，提供高性能的NIO通讯和多协议集成。提供服务动态寻址于路由、软负载均衡和容错
  • Spring Cloud
    基于SpringBoot，提供微服务架构的解决方案，支持Java。集成配置管理、服务发现、断路器、智能路由等工具
  • Motan
    微博开发， 支持Java， 提供高可用与负载均衡 。使用Netty NIO进行远程通讯，支持服务注册和订阅
  • Tars
    腾讯开发，支持C++， 提供服务发布、管理命令和心跳上报等功能。适用于高性能服务调用和微服务架构

以下是我在向microsoft copilot的问答学习的一些总结

TCP/IP 传输控制协议/互联网协议

TCP/IP是互联网通信的基础协议，它定义了输入如何从一台计算机传输到另一台计算机

  • TCP（Transmission Contro Protocol）：负责将数据分割成小包，保证数据可靠传输（有序，不丢失）
  • IP （Internet Protocol）：负责数据包的寻址和路由，即如何找到目标

📦 举个例子：TCP/IP 就像是快递系统，TCP 是打包和保证送达的过程，IP 是地址和路线规划

TLS 传输层安全协议

TLS（Transport Layer Security）是一个加密协议，用于在两个通信端建立安全连接

TLS 工作在 TCP 之上，确保数据在传输过程中不会被窃听或篡改

TLS 提供：

  • 加密，防止窃听
  • 完整性校验，防止篡改
  • 身份验证，通常使用证书

🔐 类比：TLS 就像是在快递包裹外加了一层保险箱，只有收件人能打开

HTTPS 安全的超文本传输协议

HTTPS是HTTP的安全版本，它在HTTP和TCP之间加入了TLS。所以 HTTPS = HTTP + TLS + TCP/IP

如果网站使用了HTTPS，就表示通信内容是加密的，安全性更高

🌐 举例：访问 https://www.example.com 时，浏览器会先通过 TLS 建立安全连接，然后再用 HTTP 协议传输网页内容

TLS 加密

通常我们说的加密放生在传输层之上， 不一定就在传输层。

TLS协议的加密过程主要包括以下几个方面：

  1. 握手阶段（TLS Handshake）
  • 客户端（比如浏览器）和服务器首先协商使用哪种加密算法
  • 服务器会发送自己的数字证书（通常是由CA签发），用于身份验证
  • 双方通过密钥交换算法（RSA 、ECDHE）协商出一个对称加密密钥
  1. 数据传输阶段
  • 密钥协商完成后，后续的数据传输就使用这个密钥进行对称加密
  • 即使数据被中间人截获，也无法解密内容
  1. 完整性校验
  • TLS 还会对每个数据包进行完整性校验（如HMAC），防止数据被篡改

TLS 加密过程简要说明：

  1. 客户端发起连接请求（Client Hello）：
  • 客户端向服务端发送支持的 TLS 版本、加密算法列表、随机数（Client Random）等信息。
  1. 服务端响应（Server Hello）并发送证书：
  • 服务端选择加密算法，返回自己的随机数（Server Random）。
  • 服务端发送自己的数字证书（通常是 X.509 格式），其中包含服务端的公钥和由可信 CA 签发的签名。
  1. 客户端验证服务端证书：
  • 客户端使用本地的 CA 根证书链验证服务端证书的合法性。
  • 验证通过后，客户端确认服务端身份。
  1. 密钥交换（根据不同的密钥交换算法有所不同）：

  • 如果使用的是 RSA 密钥交换（现在较少使用）：

  • 客户端生成一个预主密钥（Pre-Master Secret），用服务端证书中的公钥加密后发送给服务端。

  • 服务端用自己的私钥解密得到预主密钥。

  • 如果使用的是 ECDHE（椭圆曲线 Diffie-Hellman）：

  • 双方通过 Diffie-Hellman 协议协商出一个共享密钥，服务端的证书用于验证身份，而不是直接参与加密。

  1. 生成对称密钥：
  • 客户端和服务端使用 Client Random、Server Random 和 Pre-Master Secret 共同生成一个对称密钥（Session Key）。
  1. 使用对称密钥进行加密通信：
  • 后续的数据传输使用对称加密算法（如 AES），因为对称加密效率更高。

加密类型

TLS 中用到了两种加密方式：

加密类型 用途 特点
非对称加密 握手阶段，用于密钥交换和身份验证 安全但计算开销大
对称加密 数据传输阶段 快速高效，适合大量数据

当你访问HTTPS网站时，TLS就在背后默默完成了加密工作。

我们常说的“加密通信”、”SSL加密” （SSL 是 TLS 的前身） 基本上都是指TLS协议中实现的加密机制。

SSL 和 TLS的区别

  • SSL（Secure Sockets Layer） 是最早的加密通信协议，由Netscape 在1990年代开发
  • TLS（Transport Layer Security） 是SSL的继任者，是更安全、更现代的版本
协议版本 状态 说明
SSL 1.0 从未发布 存在严重漏洞
SSL 2.0 已废弃 存在安全问题
SSL 3.0 已废弃 被发现有严重漏洞（如 POODLE 攻击）
TLS 1.0/1.1 已废弃 安全性不足
TLS 1.2 主流使用 安全性强，广泛支持

SSL加密和TLS加密是一个同一个东西，只是“SSL”这个词更广为人知

加密算法

算法 类型 用途
AES（Advanced Encryption Standard） ✅ 对称加密 用于加密大量数据，速度快
RSA（Rivest–Shamir–Adleman） ❗ 非对称加密 用于密钥交换、数字签名
ECDHE（Elliptic Curve Diffie-Hellman Ephemeral） ❗ 密钥交换协议（基于非对称加密） 用于协商对称密钥

对称加密：加密与解密使用同一个密钥，如AES

非对称加密： 使用一对密钥（公钥与私钥），如RSA 、ECC

ECDHE是一中密钥交换协议，使用椭圆曲线密码学（ECC）实现临时密钥交换

ECC 和 ECDHE

ECC（Elliptic Curve Cryptography） 是一种非对称加密算法的数学基础

ECDHE（Elliptic Curve Diffie-Hellman Ephemeral）是基于ECC的一种密钥交换协议

ECDHE是ECDH的“临时密钥”版本（Ephemeral），每次连接都生成新的密钥对，支持前向保密（Perfect Forward Secrecy）

前向保密就是你没有版本通过截获的一个密钥对把之前的信息破获，因为每次都是新的临时密钥对，只和当前有关。

名称 类型 说明
ECC 算法基础 椭圆曲线密码学，是一类非对称加密算法的数学基础
ECDH 密钥交换协议 基于 ECC 的 Diffie-Hellman 协议
ECDHE 临时密钥交换协议 ECDH 的增强版，支持前向保密（Ephemeral）

TLS是现代加密通信的核心，使用RSA\ECDHE等非对称算法协商密钥，再用AES 等堆成算法加密数据

为什么需要ECDHE

我们知道ECDHE是一种密钥交换协议，主要作用是，在通信双方之间安全地协商出一个对称加密密钥，供后续数据加密使用。

现在TLS协议（尤其是TLS1.2 和1.3）的设计理念：

  1. 非对称加密（如RSA 或 ECDHE）
  • 用于密钥交换（协商出对称密钥）
  • 用于身份验证（如服务器证书）
  1. 对称加密（如AES）
  • 用于实际的数据传输加密
  • 加密速度快，适合大数据量通信

为什么选择ECDHE而不是传统的RSA密钥交换

  • ECDHE 支持前向保密（Perfect Forward Secrecy ,PFS）每次连接都是用临时密钥对，即使服务器私钥泄漏，历史通信内容也无法被解密。而RSA不支持。

如何实现前向保密

关键在于它使用了临时密钥对（Ephemeral Key Pair），每次连接都重新生成

  1. 客户端和服务端协商使用ECDHE算法
  2. 双方各自生成一对临时的ECC密钥对（公钥+私钥）
  • 密钥对只用于当前会话，会话结束后立即丢弃
  • 服务器的长期私钥（用于身份验证）不会参与密钥交换过程
  1. 双方交换临时公钥，并使用ECDH算法计算出相同的共享密钥（对称密钥）
  • 客户端使用 自己的私钥+ 服务端的临时公钥
  • 服务端使用 自己的私钥+客户端的临时公钥
  1. 使用这个共享密钥进行对称加密通信（如AES）

加密可以发生在哪些层

层级 示例协议/技术 加密方式 特点
应用层 HTTPS、S/MIME、JWT、PGP、gRPC、SOAP WS-Security 应用层加密 加密粒度细，可定制，跨协议，但开发复杂
传输层 TLS（用于 HTTPS、FTPS、SMTP over TLS 等） 传输层加密 通用、安全性强，适用于大多数 TCP 应用
网络层 IPSec 网络层加密 加密整个 IP 包，适合 VPN、企业内网
链路层 WPA2/WPA3（Wi-Fi）、MACsec 链路层加密 局域网/物理链路安全，防止窃听
  1. 应用层加密
  • 可以在发送JSON 、XML 、Protobuf数据之前，使用AES/RSA对内容加密
  • 适用于消息队列、数据库字段加密、REST API的敏感字段加密
  • 即使传输层被攻击，数据本身仍然是加密的
  1. 传输层加密（TLS）
  • 最常见的方式，如HTTPS 、SMTP over TLS 、gRPC
  • 加密的是整个TCP通道，应用层无需关心加密细节
  • 缺点就是 一旦TLS被破解，所有数据都会暴露
  1. 网络层加密
  • 加密整个IP包，适合VPN、企业级安全通信
  • 对应用完全透明，但配置复杂，跨网络设备兼容性差
  1. 链路层加密
  • 比如WIFI的WPA3加密，防止无线信号被监听
  • 只保护物理链路，数据离开链路后就不再安全

不同层的加密可以互补，提升整体安全性。

OPEN API的加密方式

实际开发中，Open API的加密策略会根据业务场景、安全需求、监管要求和部署环境的不同而有所差异。

一般做法

  1. 传输层加密（最常见），使用HTTPS（TLS）
  • 默认首选，大多数Open API都要通过HTTPS访问
  • 优点：简单、通用、安全，客户端和服务端都无需关心加密细节
  • 适用场景：绝大多数Web API 、RESTful API、GraphQL、gRPC等
  1. 应用层加密（增强安全)

  • 对数据本身加密

  • 请求体中的敏感字段，身份证号、银行卡号使用AES加密

  • 使用RSA公钥加密对称密钥（混合密钥）

  • 适用场景：

  • 对安全要求极高的接口，金融、医疗

  • 客户端和服务端之间存在中间代理或日志系统，避免明文暴露

  1. 签名机制（防篡改 + 身份验证）

  • 常见做法

  • 使用HMAC（如HMAC-SHA256）对请求参数进行签名

  • 使用JWT （JSON Web Token）携带用户身份和权限信息

  • 作用

  • 防止请求被篡改

  • 验证请求来源是否合法

  1. Token / API key / OAuth2
  • 用于身份验证和权限控制
  • 不属于加密本身，但通常与加密机制配合使用

加密是“防偷窥”，签名是“防篡改”

网站信任证书

HTTPS中所需要的网站信任证书，其实是指网站使用的 SSL/TLS 证书，它是实现HTTPS安全通信的核心组成部分。

网站信任证书是由受信任的证书颁发机构（CA）签发的数字证书，用于

  1. 证明网站身份，你访问的网站是真的，而不是假冒的钓鱼网站
  2. 建立加密连接，通过TLS协议

证书包含什么信息

一个标准的TLS证书通常包含

  • 网站的域名
  • 公钥，用于加密通信
  • 证书颁发机构
  • 有效期，包括起始时间和过期时间
  • 签名算法 SHA-256 RSA
  • 证书序列号和指纹

为什么叫”信任“证书

浏览器或者操作系统会内置一批”受信任的CA根证书“，当你访问一个网站时：

  1. 浏览器会检查该网站的证书是否由受信任的CA签发
  2. 如果是，认为网站时可靠的
  3. 如果不是，比如自签名证书，浏览器会弹出警告

证书在 TLS 的作用

当你访问一个使用HTTPS的网站时，TLS协议会经历一个”握手“过程，证书的作用体现在这个阶段

  1. 身份认证
  • 服务器向客户端发送自己的数字证书（通常时X.509格式）
  • 客户端验证这个证书是否受信任的CA签发，是否过期，是否匹配域名
  • 验证通过，客户端就“信任”这个服务器
  1. 密钥协商
  • 证书中包含服务器的公钥
  • 客户端使用这个公钥协商出一个对称加密密钥（通过RSA或ECDHE等算法）
  • 后续的数据传输就使用这个对称密钥进行加密

证书 != 加密，但它时加密的前提，通过证书完成身份验证与公钥传递两个功能后构建起信任关系与连接通道，再使用由证书参与的密钥协商生成的对称加密密钥加密数据传输。

TLS 会话重用

TLS 会话重用（TLS Session Resumption）是一种优化机制，用于在客户端与服务端之间建立TLS连接时跳过完整握手过程，从而提高性能、减少延迟

为什么需要 TLS 会话重用

TLS 握手过程涉及

  • 非对称加密
  • 证书验证
  • 密钥协商

这些操作计算量大，尤其在高并发场景下会影响性能。会话重用可以避免重复握手，提升效率与性能。

TLS 会话重用的两种方式

  1. Session ID (TLS 1.2支持)
  • 第一次握手时，服务器生成一个Session ID ， 发送给客户端
  • 客户端保存这个ID
  • 下次连接时，客户端发送这个Session ID，服务器查找是否由对应的会话信息
  • 如果找到，双方跳过完整握手，直接使用之前的对称密钥

📌 缺点：服务器需要维护大量会话状态，扩展性差。

  1. Session Ticket (TLS 1.2/1.3支持)
  • 第一次握手后，服务器生成一个加密的Session Ticket（包含密钥等信息），发送给客户端
  • 客户端保存这个Ticket
  • 下次连接时，客户端发送Ticket，服务器解密后恢复会话

📌 优点：服务器无状态，适合分布式架构。

TLS 1.3 的改进

  • 默认启动基于Session Ticket会话重用机制
  • 握手过程更简化，性能更高
  • 支持 0-RTT （Zero Round Trip Time）连接：客户端可以在握手前发送数据（有安全风向，需谨慎使用）

在 Java / Spring Boot 中如何使用？

  • 客户端（如 RestTemplate、WebClient）：JDK 默认支持 TLS 会话重用，无需额外配置。

  • 服务端（如 Tomcat、Netty）：

  • 如果启用 HTTPS，底层容器会自动支持 Session ID 或 Ticket。

  • 使用 TLS 1.3 时，性能优化更明显。

TCP和TLS

TCP握手

目的：传输层，建立一个可靠的连接通道

过程：

  1. 客户端发送SYN：请求建立连接
  2. 服务端回应SYN-ACK：同意连接并确认客户端的请求
  3. 客户端发送ACK：确认服务器的回应，连接建立完成

TLS握手

目的：在已建立的TCP连接上，协商加密算法、交换密钥、验证身份，从而建立一个安全的通信通道

项目 TCP握手 TLS握手
层级 传输层 应用层（基于传输层）
目的 建立连接 建立安全连接
是否加密 否 是
是否验证身份 否 是（通常验证服务器）
是否协商加密算法 否 是
