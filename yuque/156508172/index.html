K8S

Kubernates , google开源的容器编排系统，介于服务器与应用之间。 通过策略来协调与管理多个应用服务，简单的yaml文件配置，定义应用的部署顺序等信息，就可以实现自动部署到各个服务器上，并自动扩容缩容，即使宕机也能实现自动重启或部署到别的服务器上，保证服务可用。

架构原理

为了实现上述的功能，K8S会将服务器分为两种类型：

  1. 控制平面，负责控制与管理Node
  2. Node，实际运行各个应用服务

控制平面组件

Api-Server

通过调用K8S提供的接口，可以免去登录服务器输入命令去操作服务器的步骤，这些接口都是有api-server组件提供

Scheduler

负责将Pod调度到合适的Node。根据资源需求、亲和性、污点等策略选择节点，提高资源利用率。

以前我们需要登录服务器看下内存与CPU的占用情况来判断是否能在服务器上部署应用，现在这部分逻辑由Scheduler来完成。

Controller Manager

负责集群状态的自动调节。运行各种控制器（如Deployment控制器、Node控制器），确保实际状态和期望状态一致。

找到服务器后，我们需要手动关闭，重启服务，现在这个操作由Controller Manager来完成

ETCD

分布式键值存储，用于保存集群的所有状态数据。保证数据一致性与高可用。

上面的组件都会产生数据，这些数据就由etcd来负责存储

再来看看Node部分的组件

Node组件

Node是实际的工作节点， 既可以物理服务器，也可以是虚拟机，它会负责运行各个应用服务。多个应用服务共享一台Node上的内存、CPU等计算资源。

以前需要将应用代码上传到服务器上运行，使用K8S之后，需要将代码打包成（Container Imager）容器镜像，然后就可以放到服务器上运行了。

容器镜像可以简单理解为将应用代码与运行环境打在同一个压缩包里面，实现一次打包到处运行（JAVA ?）

Container Runtime

为了下载与运行镜像，Node节点中会有Container Runtime。

Pod

每个应用服务都可以认为是一个container，并且大多时候我们都会为应用服务搭配一个日志收集器或监控采集器。这些基本的containers共同组成一个一个的Pod，运行在一个Pod上:

K8S可以将Pod从一个Node移动到另一个Node:

还能以Pod为单位做重启或者扩缩容的操作：

所以在K8S中，Pod是最小的操作的单位：

Kubelet

负责Pod的生命周期管理。

前面提到控制平面会通过Controller Manager控制Node创建于关闭服务，Node上接收这些命令的组件就是Kubelet，它主要是管理和监控Node .

Kube Proxy

实现Kubernetes Service的网络代理。维护iptables或者IPVS规则，实现服务负载均衡。

负责Node的网络通讯功能。有了它外部的请求就能被转发到Node中。

Cluster

控制平面与Node共同构成一个Cluster，集群。实际使用中我们会构建多个集群，比如生产环境集群与测试环境集群。

为了将集群内部的服务暴露够外部用户使用，一般还会部署一个入口控制器Ingress

常见Ingress实现：

  • Nginx Ingress Controller
  • Traefik
  • HAProxy
  • Kong

Kubectl

一开始说到我们可以使用K8S提供的api去创建服务，我们可以自己写代码来完成，也可以使用k8s为我们准备的命令行工具kubectl ，只需要执行命令，它就会为我们调用对应的api。

怎么部署服务

  1. 编写yaml文件，在其中定义使用的镜像文件，占用的内存与CPU等信息
  2. 使用kubectl工具命令执行kubectl apply yaml
  3. kubectl会读取与解析yaml文件内容，将解析后的对应通过api请求发送给K8S控制平面的API Server， API Server会根据要求驱使Scheduler通过etcd提供的数据寻找合适的Node
  4. 让Controller Manager控制Node创建服务，Node内部的Kubelet在收到命令后给予Container Runtime拉取镜像创建容器，最终完成POD的构建。
  5. 至此服务完成创建。

整个过程，我们只需要写一次yaml文件，与执行一次kuberctl命令。

怎么调用服务

以前服务请求从外部用户通过浏览器走到Nginx服务器，然后转发到后端服务器上处理。

有了K8S之后外部请求会先到达K8S的ingress控制器，

然后被转发到K8S内某个Node的Kube Proxy上 ，再找到对应的Pod后，转发到内部的实际服务。处理结果原路返回，这是一次实际的调用。

通过上面我们可以知道，K8S本质上是应用服务与服务器之间的中间层，通过暴露一系列API能力，简化服务的部署运维流程。
