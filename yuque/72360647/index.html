  2. 掌握服务化最佳实践

推荐用法

官网学习：http://dubbo.apache.org/zh-cn/docs/user/recommend.html

超时时间，重试次数，负载方式，并发连接数

可以看到这里配置的都是线程池大小和并发数。

线程池的大小要根据表现结果来调整，参考值是200。如果在200的情况下，任务有堆积，内存还有富余，那就可以加大线程池大小。这个值不会随着增大而有相对应的效果的。如果都是数据库连接这种类型的话，加大这个连接数其实对程序没有多大的影响；而如果都是些计算任务的话，加大线程池的数量确实有效果。

并发数是考虑到有些服务的并发调用会很高，而有些服务会很低，那么就不能平均分配，同时也考虑到总的线程数量是有限的，如果被有的服务全部用光了，其他服务就调用不同的，这不是我们想看到的情况，所有在方法级别也限制了并行请求上限。

服务治理

题外话，dubbo本身没有提供链路追踪的功能，但是市面上常用的链路追踪的功能都可以应用进来，手段就是通过dubbo提供的filter扩展。后续有课分享到在猪场的实际用法。

服务治理的学习目标：

  1. 掌握服务治理的意义
  2. 掌握dubbo管理控制台的安装使用
  3. 掌握服务治理的用法
  4. 了解dubbo中提供了哪些治理行为
  5. 了解路由规则语法
  6. 了解配置规则

服务治理的意义

服务间依赖关系变得错综复杂，甚至分不清哪个应用要在哪个应用之前启动，架构师都不能完整描述应用的架构关系。

服务的调用量越来越大，服务的容量问题就暴露出来，这个服务需要多少机器支撑，什么时候该加机器？这样的管理问题是非常棘手的。这些都是服务治理要解决的问题。在dubbo里面，除了服务直接需要用到的Registry、Consumer、和Provider，还有就是Monitor，它为我们做服务治理提供了数据基础。

容器化之后我们可以对服务器进行弹性增减，这样服务治理的价值会降低嘛？我感觉容器化中的弹性服务是服务治理的一个方面，都是需要Monitor来提供依据的，并不会说取缔了服务治理。

一般我们操作的都是server部分。

条件路由

这个路由其实在之前的章节有讲到过，其中的地方是在消费者选择具体的服务提供方的时候的其中一步。

完整过程是先拿到服务提供者的完整列表，然后就是路由了，路由这一步是可以基于脚本（script）或者是条件(condition)的，从完整列表中选择出复合路由规则的提供者列表。这个路由规则是可以动态调整的。

条件路由和标签路由都是提供了路由规则。

点击创建：

可以指定service的唯一ID 或者是指定application ID，两个只能选择一个配置，对应的就是服务级别与应用级别。

通过 group:service:version 三段式来唯一标识服务。如果没有version，然后也是默认的group，那么只需要指定service就OK了。

路由规则

在配置路由规则前，我们可能会想知道服务目前是否有对应的服务治理。

像示例中的服务会对应的条件路由规则：

这个条件路由就定义了两个方法走不同的端口。之前只启动20880的服务但是调用的sayHi的方法调用失败的原因就是这个规则导致。

路由规则在发起一次RPC调用前起到过滤目标服务器地址的作用，过滤后的地址列表，将作为消费端最终发起RPC调用的备选地址。

  • 条件路由，支持以服务或Consumer应用为粒度配置路由规则
  • 标签路由，以Provider应用为粒度配置路由规则

使用简介

scope制定了是application级别 ，key就是具体的应用名字

规则详解-各字段含义

  • scope，表示路由规则的作用粒度，scope的取值会决定key的取值。必填。

  • service 服务级别粒度

  • application 应用级别粒度

  • key，明确规则体作用在哪个服务或应用。必填

  • scope=service时，key的取值为[{group}:{service}:{version}]的组合

  • scope=application，key的取值为application name

  • enable=true，表示当前路由规则生效，可不填，默认为生效

  • force=false，表示当路由结果为空时，是否强制执行，如果不强制执行，路由结果为空的路由规则将自动失效，可不填，默认为false

  • runtime=false，是否在每次调用时执行路由规则，否则只在提供者列表变更时预先执行并缓存结果，调用时直接从缓存中获取路由结果。如果用了参数路由，那么必须设为true，需要注意设置会影响调用的性能，可不填，缺省为false

  • priprity=1，路由规则的优先级，用于排序，优先级越大越靠前执行，可不填，默认为0

  • conditions， 定义剧吐的路由规则内容，必填

我们来重点关注一下conditions这块，它是规则主体，由1到任意多的规则组成，本身是yml的格式。

规则体

  1. 格式
  • => 之前部分为消费者匹配条件，所有参数和消费者的URL进行对比，当消费者满足匹配条件时，对该消费者执行后面的过滤规则
  • => 之后为提供者地址列表的过滤条件，所有参数和提供者的URL进行对比，消费者最终只拿到过滤后的地址列表
  • 如果匹配条件为空，表示对所有消费方应用，如：=>host!=10.20.153.11
  • 如果过滤条件为空，表示禁止访问，如：host=10.20.153.10 =>
  1. 表达式

  • 参数支持

  • 服务调用信息，如：method，argument等，暂不支持参数路由

  • URL本身字段，如：protocol，host，port等

  • URL上的所有参数，如：application，organization等

  • 条件支持

  • 等号 = 表示匹配

  • 不等号 != 表示不匹配

  • 值支持

  • 以逗号 ,分隔多个值，如：host != 10.20.153.10,10.20.153.11

  • 以星号 *结尾，表示通配，如：host !=10.20.*

  • 以美元符 $开头，表示引用消费者参数，如：host=$host

  1. 具体实例
  • 排除预发布机：=> host !=172.22.3.91
  • 白名单：host != 10.20.153.10,10.20.153.11 =>
  • 黑名单：host = 10.20.153.10,10.20.153.11 =>
  • 服务寄宿在应用上，只暴露一部分机器，防止整个集群挂掉：=>host=172.22.3.1*,172.22.3.2*
  • 为重要应用提供额外的机器：application != kylin =>host!=172.22.3.95.172.22.3.96
  • 读写分离：method=find*,list*,get*,is*=>host=172.22.3.94,172.22.3.95.172.22.3.96
    method!=find*,list*,get*,is*=>host=172.22.3.97,172.22.3.98
  • 前后台分离：application =bops=>host=172.22.3.91,172.22.3.92,172.22.3.93
    application !=bops=>host=172.22.3.94,172.22.3.95,172.22.3.96
  • 隔离不同机房网段：host!=172.22.3.* =>host!=172.22.3.*，以为这网段为3的，才能访问3段的，其他网段不能访问到3段的服务
  • 提供者与消费者部署在同集群内，本机只访问本机的服务： =>host=$host，任何消费者都是访问的自己地址的服务

标签路由

标签路由通过将某一个或多个服务的提供者划分到同一个分组，约束流量只能在指定的分组中流转，从而实现流量隔壁的目的，可以作为蓝绿发布、灰度发布等场景的能力基础。

大白话就是给机器打上标签，相同的标签的归为一组。

Provider端

Provider标签主要是指对Provider端应用实例的分组，目前有两种方式可以完成实例分组，分别时动态规则打标和静态规则打标，其中动态规则优先级更高，当两种规则出现冲突时，以动态规则为准。

  • 动态规则打标，可随时在服务治理控制台下下发或修改标签归组规则
  • 静态打标
    <dubbo:provider tag="tag1"> or <dubbo:service tag="tag1"> or

consumer端

RpcContext.getContext().setAttachment(Contants.REQUEST_TAG_KEY,"tag1");
