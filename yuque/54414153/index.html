CopyOnWriterArrayList

在使用互斥锁的实现时，会出现性能问题，因为线程只能挨个访问。于是有了读写锁（ReadWriteLock），用来处理读多写少的场景；而为了进一步处理写锁被占用时间过长，导致读操作被大量阻塞的情况，就出现了CopyOnWrite这种实现。

copyOnWriter的实现思想是在写之前将数组对象复制一份副本B，去写新的那一份副本B，读取的时候还是读的原来的A，并且不加锁，写完成之后将数组的引用指向B，这样就保证了写的时候也能读取。就注意的是：如果对数据的版本有要求，就不要用这种。

CopyOnWriterArrayList是利用这种思想实现的。

写的时候会加锁，保证只有一个写在执行，只有一个副本。同一时刻还是只能有一个线程对数组进行修改。而后新建了长度为原本数组长度+1的新数组，并把新元素放到了最后，然后把数组引用切换指到新数组上。

getArray()方法拿到当前的数组，然后长度+1后设置好新值，将当前数组引用切换到新的数组。

思考：这种副本的拷贝行为和扩容，哪种对内存影响更大（占用更多内存）？

答：拷贝对内存影响更大。在数组的扩容，数组里面存放的是数据的引用，而非数据本身，所以扩容占用内存不大。而copy用的拷贝是对数据的完全拷贝（深拷贝，不可能是浅拷贝，因为浅拷贝得到的效果不是copyOnWrite要达到的目的），数据是会被完全拷贝两次，数据会膨胀，占用额外的内存。

加同步锁保证只能有一个线程去修改，然后暴露一个array的数组引用，让线程去访问这个引用，而copyOnWrite在操作的时候就是在修改实际的数组。

通过切换array指向的数组对象就可以控制访问的实际数组对象。

copyOnwrite是在读非常多而写非常少的场景下使用的，并且还要考虑数组复制两份会不会内存不足的问题。在这种机制，写操作是有一定延迟的，并不保证数据的实时一致性，只能保证到最终一致性。

Set

如何使用HashMap来实现HashSet？我们知道Set是元素不能重复，而Map是Key值不能重复，所以我们假设一下是不是可以使用Map中的Key来作为Set中的元素，value值我们肯定让它的负担最小最好，所以value中我们存储一个对象的引用。 key对我们来说是有意义的，而value对我们来说是没有意义的。(value存null的结果也是一样的，内存占用应该也是差不多，所有JDK没有直接存null)

ArrayBlockingQueue

queue提供的方法本身是比较简单的。queue也有各种实现类，ArrayBlockingQueue是一种用数组实现的阻塞队列。

如何用数组来实现一个队列呢？循环数组， 通过数组的首尾相连。我们使用两个Index来保存存入元素时的Index信息，数组满了之后就会回到第一位等待读取后再压入，

当我们调用入队列的方法的时候putIndex会告诉我们应该存到哪个位置，调用出队列的方法的时候takeIndex会告诉我们应该从哪个地方去取数据，第一个元素进来时候putIndex为0，那么我们就放到第一位，然后把putIndex改为1，第二个元素来了putIndex为1，那么第二个元素就会去到第二位，putIndex改为2，以此类推。当队列元素满了的时候putIndex就会变为0，这时候再来存元素就会阻塞，等待元素被读取，需要去take数据。take也是差不多一个意思。

ConcurrentLinkedQueue

ArrayBlockingQueue与LinkedBlockingQueue 都是线程安全的，提供ConcurrentLinkedQueue是为了更好的并发性能，所以ConcurrentLinkedQueue没有提供阻塞的put方法。

来看看offer，看之前我们可以思考一下，如何提高我们的并发性。

我们先拿到队列的尾部元素tail 赋值给p和t，p.next赋值给q，如果q为null，即p是最后一个元素，那么我们就CAS把p.next指向新元素，成功之后p和t就不一样了，这时候我们把tail指向新元素，就完成了元素添加的操作。后面else if的操作没看懂，p.next在什么情况下会等于q。

明白了，无锁编程核心机制CAS！

SynchronousQueue

一种非常特殊的同步队列。在线程池的时候我们有用到这种队列。这个队列我们就不在这里剖析源码了，会另外出一篇笔记专门讲这个，本次注重使用。

之前我们学的三种实现都是提供一个队列存储元素，并提供先入先出的操作特性。而SynchronousQueue的队列容量始终为0。

这就照成了如下几种情况：

  1. 如果有个线程来做put操作，如果没有线程来take，那么这个put的线程就会一直阻塞
  2. take会阻塞直到有线程来put。
  3. 如果你是调用offer方法的话，如果没有take方法在你之前等待，offer的元素会丢失
  4. poll取不到元素会返回null，如果有put线程阻塞，那就可以正常取到，即poll不是阻塞的方法
  5. peek永远都返回null，因为peek需要拿到队列里面的元素再去减少，这种实现队列里面是没有元素的。

实例代码在Demo_SyncQueueTest.java
