限流

限流是分布式微服务中需要考虑的一个问题。

常见做法

🧠 一、常见限流算法及优缺点

算法 原理 优点 缺点 适用场景
固定窗口计数 在固定时间窗口内计数，如每秒最多100次 实现简单，性能高 边界问题明显，突发流量可能超限 简单接口限流
滑动窗口计数 记录每次请求时间，统计最近时间段内请求数 精度高，平滑流量 实现复杂，性能略低 精细限流控制
令牌桶（Token Bucket） 固定速率生成令牌，请求消耗令牌 支持突发流量，灵活性高 实现稍复杂 接口限流、用户限流
漏桶（Leaky Bucket） 固定速率处理请求，超出速率的请求被丢弃 平滑流量，防止突发 不支持突发流量 网关限流、流量整形
匀速排队 请求排队，按固定速率处理 控制请求节奏，防止拥塞 延迟高，不适合高实时性场景 服务保护、后台任务处理

🧰 二、主流限流组件及优缺点

✅ 1. Sentinel（阿里巴巴开源）

  • 支持算法：QPS、匀速排队、关联限流、链路限流

  • 优点：

  • 控制台可视化配置

  • 支持动态规则更新

  • 支持熔断、降级、系统保护

  • 缺点：

  • Java 专用，非通用组件

  • 分布式部署需额外配置

  • 适用场景：微服务限流、服务调用链路保护、热点参数限流

✅ 2. Bucket4j

  • 支持算法：令牌桶（支持 Redis、Hazelcast 等后端）

  • 优点：

  • 高性能，支持分布式

  • 支持多维度限流（IP、用户、接口）

  • 缺点：

  • 控制台管理需自建

  • 漏桶支持较弱

  • 适用场景：Spring Boot 项目、网关限流、用户行为限流

✅ 3. Spring Cloud Gateway Redis RateLimiter

  • 支持算法：令牌桶（Redis + Lua）

  • 优点：

  • 原子性强，适合分布式

  • 配置简单，集成方便

  • 缺点：

  • 仅限网关层使用

  • 不支持复杂限流策略

  • 适用场景：网关限流、接口访问控制

✅ 4. Resilience4j

  • 支持算法：RateLimiter（令牌桶）、Bulkhead、CircuitBreaker

  • 优点：

  • 轻量级，函数式编程友好

  • 与 Spring Boot 深度集成

  • 缺点：

  • 不支持控制台管理

  • 分布式支持需自建

  • 适用场景：单体应用限流、服务容错保护

✅ 5. Guava RateLimiter

  • 支持算法：令牌桶

  • 优点：

  • 极简 API，易用

  • 缺点：

  • 不支持分布式

  • 不支持动态配置

  • 适用场景：本地限流、单机应用

🧭 三、选型建议

场景 推荐组件 原因
网关层限流 Spring Cloud Gateway Redis RateLimiter / Bucket4j 高性能、支持 IP/路径限流
微服务内部限流 Sentinel 控制台管理、支持多种策略
单体应用限流 Guava / Resilience4j 简单易用、轻量级
分布式限流 Redis + Bucket4j / Sentinel 支持 Redis 存储，适合集群环境

使用Redis实现限流

我们在以往的学习中或许知道了实现限流的一些算法，但是如何运用到实际的场景更值得思考，比如如何将限流和Redis结合，利用Redis的特性实现限流。

主要是以下实现方式

固定窗口计数法（Fixed Window Counter）

使用 Redis 的 INCR 命令对某个 key 进行计数。
设置 key 的过期时间为时间窗口长度（比如 1 秒、1 分钟）。
如果计数超过阈值，则拒绝请求。

滑动窗口（Sliding Window）

更精确的限流方式，记录每次请求的时间戳。
可以使用 Redis 的 ZADD 和 ZRANGE 来维护一个时间戳集合。
删除过期时间戳，只保留当前窗口内的请求记录。

令牌桶算法（Token Bucket）

Redis 存储当前令牌数量。
定时任务往桶里添加令牌。
每次请求消耗一个令牌，没有令牌则拒绝。

漏桶算法（Leaky Bucket）

类似令牌桶，但更适合平滑流量。
Redis 存储请求队列，按固定速率处理请求。

使用 Redis + Lua 脚本

为了保证原子性，限流逻辑通常用 Lua 脚本实现。
可以将计数、判断、过期等操作封装在一个脚本中执行，避免并发问题。
