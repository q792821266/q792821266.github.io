详细介绍

下面是各个区域的介绍

Heap 堆

介绍

首先是Heap堆。堆是OOM故障最主要发生的区域。它是内存中最大的一块区域，被所有线程共享，存储着几乎所有的实例对象、数组。所有的对象实例以及数组都要在堆上分配， 随着编JIT编译器的发展与逃逸分析技术逐渐成熟，栈上分配、标量替换优化技术会导致一些微妙的变化，所有对象都分配在堆上也就没有那么绝对了。

JAVA堆是垃圾手机管理的主要区域，所以很多时候也被称为”GC堆”。从内存回收的角度来看，由于现在收集器基本都采用分代收集算法， 所以堆可以被细分为：新生代和老年代，再细致一点就有Eden空间，From Survivor空间、To Survivor空间等。从内存分配的角度来看，线程共享的堆中可能划分出多个线程私有的分配缓存区（Thread Local Allocation Buffer,TLAB）。不过无论如何划分，都与存储的内容无关，存储的仍然是实例对象，不同的划分方式目的是为了更好的回收内存，或者更快地分配内容。

调整

根据JVM的规范，JAVA堆可以处理物理上不连续的内存空间中，主要逻辑上是连续的即可。在实现上，既可以是固定大小的，也可以在运行时动态调整。

如何调整

通过设置参数，可以设定堆区的初始值和最大值，比如：

-Xmx256M -Xmx 1024M

其中-X表示它是JVM运行时参数，ms时memory start的简称，即内存初始值，mx是memory max简称，即最大内存。

值得注意的是，在通常情况下，服务器在运行过程中，堆空间不断地扩容与回缩，会线程不必要的系统压力，所以在线上生产环境中，JVM的Xms和Xmx会设置同样大小，避免在GC后调整堆大小带来的额外压力。

堆的默认空间分配

先看一下堆空间内存分配的大体情况。

如果你想配置这个比例，要怎么修改呢？

使用 java -XX:+PrintFlagsFinal -verison 可以看到当前JDK版本所有默认的JVM参数。

我们关注与堆内存分配相关的两个参数

  1. -XX:InitialSurvivorRatio ：新生代Eden/Survivor空间的初始比例
  2. -XX:NewRatio：Old区/Young区的内存比例

因为新生代是由Eden + S0 + S1组成的，所以按照上述默认比例，如果eden区内存大小是40M，那么两个survivor区就是5M，整个young区就是50M，然后可以算出Old区内存大小是100M，堆区总大小就是150M

溢出演示

使用-XX:+HeapDumpOnOutOfMemoryError 可以让JVM在遇到OOM异常时，输出堆内信息，对于相隔几个月才出现的IIM尤其重要

一个新对象的内存分配流程

绝大部分对象都是在Eden区生成，当Eden区填满时，会触发Young Garbage Collection， 即YGC。垃圾回收的时候，在Eden区执行清除策略，没有被引用的对象直接回收。依然存活的对象会移送至Survivor区。Survivor区分为s0,s1两块内存空间，YGC的时候，它们将存活的对象复制到未使用的那块空间，然后将当前正在使用的空间完全清除（复制-清除算法），交换两块空间的使用状态。如果YGC要移送的对象大于Survivor区容量的上线，则直接移交老年代。

一个对象不能永远呆在新生代。JVM中 XX:MaxTenuringThreshold 参数就是来配置一个对象从新生代到老年代的阈值。默认时15，即在Survivor区交换14次，经历15次垃圾回收，晋升至老年代。

元空间Metaspace

在HotSpot JVM中，永久代（≈方法区）中用于存放类和方法的元数据以及常量池，比如Class 和 Method。每当一个类初次被加载的时候，它的元数据都会放到永久代中。

永久代是有大小限制的，因此如果加载的类过多，很可能导致永久代内存溢出，即万恶的java.lang.OutOfMemoryError:PermGen ，为此我们不得不对虚拟机做调优。

那么，Java 8中PermGen为什么会被移出HotSpot JVM了？ （详见JEP 122:Remove the Perimanent Generation)

  1. 由于PermGen 内存经常会溢出，引发恼人的 java.lang.OutOfMemoryError:PermGen， 因此JVM的开发者希望这一块内存可以更灵活地被管理，不要再经常出现这样的OOM
  2. 移除PermGen 可以促进HotSpot JVM与JRockit VM的融合，因为JRockit没有永久代

根据上面的各种原因，PermGen最终被移除，方法区移动到了Metaspace，字符串常量池移到了堆区。

更准确地说，Perm区中的字符串常量池被移到了堆内存中是在Java 7中，Java 8时 PermGen 被元空间代替，其他内容比如类元信息、字段、静态属性、方法、常量等都移动到元空间区。比如 java/lang/Object 类信息、静态属性System.out、整型常量1000等。

元空间本质和永久代类似，都是堆JVM规范中方法区的实现。不过元空间与永久代之间最大的区别在于：元空间并不在虚拟机中，而是使用本地内存。因此，默认情况下，元空间的大小仅受本地内存限制。（和后面提到的直接内存一样，都是使用本地内存）

相关的JVM参数

参数 作用
-XX:MetaspaceSize 分配给Metaspace(以字节计算）的初始大小
-XX:MaxMetaspaceSize 分配给Metaspace的最大值，超过此指就会触发Full GC，此值默认没有限制，但应取决于系统内存的大小，JVM会动态地改变此值。
-XX:MinMetaspaceSizeFreeRatio 在GC之后，最小的Metaspace剩余空间容量的百分比，减少为分配空间所导致的垃圾收集
-xx:MaxMetaspaceSizeFreeRatio 在GC之后，最大的Metaspace剩余空间容量的百分比，减少为释放空间所导致的垃圾收集

更多关于Metaspace的介绍，还是看看官方文档或。

虚拟机栈

对于每一个线程，JVM都会在线程被创建的时候创建一个单独的栈，也就是说虚拟机栈的生命周期和线程是一致的，并且时线程私有的。出了Native方法以外，Java方法都是通过Java虚拟机栈来实现调用和执行过程的（需要程序计数器、堆、元空间内数据的配合）。所以Java虚拟机栈是虚拟机执行引擎的核心之一。而Java虚拟机栈中出栈入栈的元素就成为”栈帧“。

栈帧（Stack Frame)是用于支持虚拟机进行方法调用和方法执行的数据结构。栈帧存储了方法的局部变量表、操作数栈、动态连接和方法返回地址等信息。每一个方法从调用至执行完成的过程，都对应着一个栈帧在虚拟机栈里从入栈到出栈的过程。

栈对应线程，栈帧对应方法

在活动线程中，只有位于栈顶的帧才是有效的，称为当前栈帧。正在执行的方法称为当前方法。在执行引擎运行时，所有指令都只能针对当前栈帧进行操作。而StackOverFlowError表示栈溢出，导致内存耗尽，通常出现在递归方法中。

虚拟机栈通过pop和push的方式，对每个方法对应的活动栈帧进行运算处理，方法正常执行结束，肯定会跳转到另一个栈帧上。在执行过程中，如果出现异常，通常会进行异常回溯，返回地址通过异常处理表确定。

栈帧在JVM体系的地位是非常高的，下面是他的具体结构信息。

局部变量表

局部变量表是存放方法参数和内部定义的局部变量的区域

局部变量表所需要的内存在编译期间完成分配。当进入一个方法时，这个方法需要在帧中分配多大的局部变量空间时完全正确的，在方法运行期间不会改变局部变量表的大小。

如果局部变量是Java的8中基本数据类型，则存在局部变量表中，如果是引用类型，比如new 出来的String，局部变量表存放对应的引用，实例则在堆中。

操作数栈

操作数栈（Operand Stack），名字告诉我们是一种Stack栈结构。Java虚拟机的解释执行引擎称为“基于栈的执行引擎”，这个栈指的就是操作数栈。当JVM为方法创建栈帧的时候，在栈帧中为方法创建一个操作数栈，保证方法内执行可以完成工作。

方法返回地址

方法执行时有两种推出情况：

  • 正常退出，即正常执行到任何方法的返回字节码执行，入RETURN、IRETURN、ARETURN等
  • 异常退出

无论何种退出情况，都将返回至方法当前被调用的位置。方法退出的过程相当于弹出当前栈帧，退出可能有三种方式：

  • 返回值压入上层调用栈帧
  • 异常信息抛给能够处理的栈帧
  • PC计数器执行方法调用后的下一条指令

本地方法栈

本地方法栈和虚拟机栈的作用时类似的，只是本地方法栈时为虚拟机需要用到的Native方法服务，而虚拟机栈是为执行Java方法（字节码）服务。

在虚拟机规范中对本地方法栈中方法使用的语言、使用方式与数据结构并没有强制规定，因此可由虚拟机自由实现。也有的虚拟机（Sun HotSpot）直接把本地方法栈和虚拟机栈合二为一。与虚拟机栈一样，本地方法栈区域也会抛出StackOverFlowError和OutOfMemoryError异常

程序计数器

Program Counter Register ，这是一块比较小的内存空间。是线程私有的。它可以理解为当前线程所执行的字节码的行号指示器。因为代码在执行时，线程有可能会被挂起，CPU一会执行线程A，一会执行线程B，再切换的时候就需要有地方告诉CPU执行到哪。

为了线程切换后能恢复到正确的执行位置，每条线程都需要有一个独立的程序计数器，各条线程之间计数器互补影响，独立存储。每个线程在创建后，都会产生自己的程序计数器和栈帧，程序计数器用来存储执行指令的偏移量和行号指示器等，线程执行和恢复都需要依赖程序计数器，这个区域不会发生内存溢出异常。

直接内存

直接内存（Direct Memory)并不是虚拟机运行时数据区的一部分，也不是Java虚拟机规范中定义的内存区域，但是确实被频繁使用的，而且也是可以导致OutOfMemoryError异常。

JDK 1.4的时候加入了 NIO （New Input / Output）类，引入了一种基于通道（Channel）与缓冲区（Buffer）的IO方式，它可以使用Native函数库直接分配堆外内存，然后通过一个存储在堆内的DirectByteBuffer对象作为这块堆外内存的引用进行操作。这样在一些场景下能显著提高性能，避免了在Java堆与Native堆来回复制数据。

直接内存并不会收到Java堆大小的限制，但是也是一块内存，所有收到物理机的内存限制（包括RAM及SWAP区或者分页文件）以及处理器寻址空间的限制。如果内存区域总和大于物理内存的限制，也是会OOM的。

Code Cache

简而言之，JVM代码缓存时将JVM将其字节存储为本机代码的区域。我们可以将可执行本机代码的每个块称为nmethod，这个nmethod可能是一个完整的或内联的Java方法。

实时编译器（JIT）时代码缓存区域最大的消费者。这就是为什么一些开发人员将其内存称为JIT代码缓存的原因。

这部分代码所占用的内存就被称为Code Cache区域。一般情况下我们不会关心这部分。如果这部分OOM了，就会看到日志中出现 java.lang.OutOfMemoryError code cache。
