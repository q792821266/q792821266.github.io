HashMap在JDK1.7

言归正传，我们知道HashMap作为一个集合类，经常被用来存储数据。既然是要存储数据，那么底层必须有存储数据的结构，那么HashMap的存储结构是什么样的？

HashMap 先根据 key 的 hash 定位数组中的桶，再在桶内比较 key，找到对应的值。JDK 7 的 indexFor 使用 hash & (length - 1) 计算桶下标，数组长度为 2 的幂。不同的 key 可能落入同一桶，由链表保存；同一个 key 再次 put 时更新其值，不会为它另建一条重复映射。下面的 addEntry 展示了新增节点的过程。

值得注意的是这个createEntry方法中，先获取了原来index下的Entry，然后把原来的Entry作为参数创建了一个新的Entry作为table[index]，这样等于说将新的元素插入到了链表的头部。

既然数据存储结构是个数组，那么数组必定有个初始长度，那么HashMap的table初始长度是多少呢？这个问题我们可以通过构造方法可以得知，因为初始化的操作一般都会在构造的时候就确定。

默认初始容量是 16，负载因子是 0.75。容量表示桶数组的长度；16 × 0.75 = 12 是通常的扩容阈值，不能把 12 当作数组容量。JDK 7 的不同更新版本在数组初始化时机和扩容触发细节上有所差异，调试时应以使用的源码版本为准。

数组创建后长度固定，但 HashMap 可以分配更大的数组来容纳新增数据。随着映射数量增长，达到实现规定的扩容条件时，resize 会分配新表；常见的扩容倍率是 2。这里要区分元素数量、桶数组容量和扩容阈值。扩容有助于减少桶内拥挤，但如果大量 key 的哈希仍然冲突，链表依然可能很长。

\

扩容后数组长度改变，原来的桶下标可能不再适用，所以要把旧表中的节点重新分配到新表。这里的重点是按新数组长度重新计算下标；不能理解为每次迁移都必须重新调用所有 key 的 hashCode 方法。

我们为什么说HashMap是线程不安全的呢？就看着下图modCount++这个操作没有任何并发控制，就可以说明它线程不安全了。

总结

HashMap 使用桶数组和链表保存映射。落入同一桶的不同 key 形成链表，JDK 7 新增节点时使用头插方式。默认初始容量为 16，负载因子为 0.75，通常的扩容阈值为 12；扩容一般将桶数组长度翻倍，再重新分配节点。

HashMap 是线程不安全的，比如put方法中 modCount++这样的操作产生的原子性问题。

ConcurrentHashMap

JDK 7 中的 ConcurrentHashMap 是线程安全的 Map，不允许 null key 或 null value。它使用 Segment 数组组织数据，每个 Segment 管理自己的桶数组和链表，并对修改操作加锁。下面按这两个层次观察它的结构。

JDK 7 中 Segment 数组的长度在构造时确定，之后不会随元素增长而增加；扩容发生在某个 Segment 内部的桶数组中，由该 Segment 的 rehash 方法完成。OpenJDK 7 源码

实现原理

使用了新的数据结构Segment来存储数据，这是一种特殊的hashTable（hashTable可以简单的认为是加了锁的hashMap，线程安全，使用同步锁实现，效率较低），每一个segment都是线程安全的。所以并发访问的时候，并发度是受到segment个数的影响所控制的(同步锁)，这种方式有点类似分段锁，将大的数据结构分为若干个小的，然后对小的数据加锁。

每个 Segment 内部使用数组和链表存储条目。Segment 继承 ReentrantLock，以复用锁机制来保护该分段内的修改操作。

结构

  • concurrencyLevel：构造时用于估算并发更新程度，默认值为 16；Segment 数量按该值向上取到 2 的幂。不同 Segment 的更新可以并行，同一 Segment 的更新需要竞争其锁，因此不能保证任意 16 个写线程都互不阻塞。
  • initialCapacity：整个 Map 的初始容量估计值，内部按 Segment 分配并调整。
  • loadFactor：各 Segment 内部桶数组的负载因子。
  • threshold：各 Segment 的扩容阈值，通常由其桶数组长度乘负载因子得到。

Segment 在持有自身锁时扩容内部桶数组，保证分段内结构修改的线程安全。这不代表业务中的多个 Map 操作会自动组成原子操作。

ConcurrentHashMap初始化时会初始化第一个Segment[0]，其他的Segment都是在插入第一个值得时候进行初始化的。为什么要初始化Segment[0]呢 ？后面使用了这个值的当前值的数组长度和负载因子来初始化Segment[k]，要注意的是当前值，因为初始化使用的Segment[0]有可能已经被扩容。

HashMap在JDK1.8

JDK 8 的 HashMap 在桶数组和链表之外引入了红黑树桶。是否树化同时取决于桶内节点数量和桶数组容量；当 treeifyBin 被调用而数组长度小于 64 时，会先扩容。不能只根据“超过 8 个节点”断言一定转成红黑树。OpenJDK 8 HashMap 源码

JDK1.8的concurrentHashmap

JDK 8 的 ConcurrentHashMap 不再以 Segment 作为常规存储和加锁单位，底层采用桶数组、链表及树桶。空桶插入主要使用 CAS，非空桶更新通常对桶的首节点加锁；如果正在扩容，还可能参与数据迁移。原有 Segment 相关定义主要用于序列化兼容。OpenJDK 8 ConcurrentHashMap 源码

可以看到put代码里面是有同步代码块的，但是这个同步锁就和1.7的实现有所区别。

JDK 7 的多个桶共享一个 Segment 锁；JDK 8 的非空桶更新通常只竞争目标桶的锁，锁定范围因而更细。桶内仍可能发生冲突，所以更细的锁粒度并不意味着所有并发写入都无需等待。
