三、第一步：文档切分（比你想象的重要）

  • 随机按 token 切

  2. 代码块
  3. 段落

四、第二步：Embedding（向量化）

这里说一句非常工程化的话：

Embedding 模型不需要“聪明”，只需要“稳定”。

✅ Embedding 模型的职责

  • 把语义相近的文本 → 映射到向量空间中接近的位置
  • 不负责推理、不负责生成

✅ 工程建议（不选具体厂商）

✅ 维度建议

768 通用性最佳，384‑512 更省空间

✅ 嵌入策略

  • 离线向量化
  • 不要在 query 时才 embed 全文
  • 文档变了才重建

✅ 一个非常重要的点（90% 新手忽略）

Embedding 和 LLM 可以完全不是同一个模型系统。

  • 你可以：

  • 本地 embedding

  • 云模型生成回答

  • 两者完全解耦

六、第四步：Retrieval（理解 RAG 的核心）

这是 RAG 真正“是否聪明”的地方。

❌ 错误做法（最常见）

✅ 正确 Retrieval 分层策略

✅ Step 1：向量检索（语义）

✅ Step 2：规则 / 元数据过滤

例如：

  • 同一篇文章优先
  • 同一 tag 优先
  • 最近时间优先

✅ Step 3：压缩 / 重排序（非常省 token）

甚至可以：

  • 再用一个小模型
  • 或简单打分规则

✅ Step 4：再交给 LLM

并且：

RAG 内容必须是“引用材料”，不是“背景材料”。

八、视频 / 音频怎么进 RAG？（不展开，但给你正确路径）

RAG 只认“文本”。

所以：

RAG 从来不直接理解音视频。

九、给你一个“不会翻车”的落地顺序（非常关键）

如果你今天开始做：

✅ Day 1–2

  • 文本 → chunk → embedding → FAISS
  • 能查到正确段落 ✅

✅ Day 3

  • 加 metadata
  • 加 Top‑K 控制

✅ Day 4

  • 接进 Agent，做成一个 Skill

到这一步，你就已经拥有80% 实际价值。

十、一句话总结（可以当座右铭）

RAG ≠ 高大上系统**
**RAG = 稳定切分 + 可控检索 + 克制上下文

只要你做到：

  • chunk 切得合理
  • 检索不过量
  • 上下文严格受控

RAG 的效果就会非常可靠，而且成本极低。
