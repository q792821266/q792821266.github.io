6. 日程助手想读 OA 数据：引入 OAuth 委托授权

6.1 新需求：让第三方替小林做一件有限的事

公司接入第三方日程助手，希望它每天读取小林的 OA 日程并提醒他。

日程助手属于另一套应用。它需要调用 OA 的日程 API³⁰，却不应该拿到小林的 OA 密码，也不应该拥有删除报销、读取所有员工资料等权限。

这时的问题是：

小林如何允许日程助手，在有限范围和时间内，代表自己访问 OA 日程？

这叫委托授权。OAuth 2.0³⁷ 就是处理这类问题的授权框架。

这个名称对应的正是本例要做的事：小林不给日程助手自己的密码，而是通过身份平台授予有限的访问范围；平台按规则签发访问令牌，助手用令牌调用 OA，OA 再检查是否允许访问。

OAuth 2.0 为这类交互约定参与角色、申请授权、取得令牌和使用令牌等规则。它不是另一个需要登录的业务系统，也不是某种令牌文件格式。接下来几节会把上述步骤具体展开。

后文为简洁而写的“OAuth”，均指这里的 OAuth 2.0，不是在引入另一个概念。先记住它解决的问题：让应用在没有用户密码的情况下，获得受限的资源访问能力。

6.2 不能直接复用 OA 的浏览器会话吗

OA Session³⁸ Cookie 是 OA 为浏览器交互建立的凭据，通常代表较广的应用会话。把它交给第三方，难以清楚表达“只读日程”，也会让第三方获得不必要的能力。

我们需要一种专门的访问凭证，说明被允许的范围，并能管理有效期和撤销。OAuth 把这种凭证称为 Access Token³⁹，访问令牌。

6.3 谁来签发 Access Token

系统需要一个组件来完成这些职责：

  • 识别提出申请的应用。
  • 确认用户身份及授权依据，必要时让用户确认范围。
  • 按策略签发和管理令牌。

OAuth 把承担这组职责的角色叫 Authorization Server，即授权服务器。

它是职责名称，不要求物理上增加一套服务器。 现有统一认证平台如果支持 OAuth，就可以同时承担这组职责。

也可以将这些职责拆到不同服务。但拆分是部署与产品设计选择，不是看到新术语就必须增加一台服务器。

6.4 四个角色，一一对应到本例

OAuth 角色 本例是谁 做什么
Resource Owner，资源所有者 小林 决定是否允许日程助手访问自己的日程，受平台策略限制
Client²⁸，客户端 日程助手 申请访问，并携带令牌调用 API
Authorization Server，授权服务器 具备 OAuth 能力的统一身份平台 处理授权并签发令牌
Resource Server⁴⁰，资源服务器 提供日程 API 的 OA 验证令牌并执行访问控制

这里的 Client 是申请访问资源的应用，不专指浏览器。OA 被叫作资源服务器，是因为它提供受保护的 API；它仍然是原来的 OA。

6.5 新问题：访问令牌怎样安全交给日程助手后端

先明确本例的部署：日程助手有自己的后端，后端负责定时读取 OA 日程，浏览器只负责用户点击、跳转和交互。访问令牌需要交给日程助手后端，由后端保存和使用。

为什么这时要继续考虑另一种交付方式？因为这里的访问令牌具有实际的 API 访问能力。对于“持有即可使用”的访问令牌，拿到令牌的人可能在有效期和授权范围内调用接口，不需要知道小林的密码。

如果令牌经过浏览器，就需要防止它进入不该接触它的脚本、存储、URL 历史、日志等位置。并非每次浏览器传递都会泄露，但在本例有受保护后端的前提下，可以选择减少真正访问令牌暴露给浏览器的机会。

这里才出现新的设计目标：浏览器必须参与跳转，但访问令牌应通过受保护的服务端连接交给符合条件的日程助手后端。

这不同于前面“让 OA 验证用户并建立本地会话”的问题，也不意味着第 4 节的签名凭证方案无法实现安全 SSO。

6.6 方案：浏览器转交授权码，后端再兑换访问令牌

为了达到这个目标，认证中心先通过浏览器返回一个短期、一次性的授权码⁴²，下面记为 T。真实协议用参数名 code 传递这份授权码，所以后面看到的 code 就是这里的 T。T 用于后续兑换，不能直接拿去读取 OA 日程；访问令牌暂时不经过浏览器。

日程助手后端通过 HTTPS 向认证中心兑换。认证中心不仅检查 T，还按协议检查目标应用、回调约束、适用的客户端身份验证和兑换绑定条件，之后才把访问令牌直接返回给后端。R2

以能保管应用凭据的后端为例：攻击者只截获 T，却无法满足客户端身份验证或相应兑换绑定条件，就不应兑换成功。因此，增加这一阶段的意义不只是把令牌换成一个更短的字符串，而是把“浏览器转交”与“符合条件的后端取得真正令牌”分开。

现在才引入“中间凭证”这个分类：授权码位于申请授权与取得访问令牌之间，所以属于中间凭证。它不是所有登录流程都必须增加的一层，而是本节所选授权码流程中的交付机制。

服务端之间直接通信称为后通道⁴¹。实际接入还需要正确的事务关联和 PKCE⁴³ 等保护，第 9 节会具体解释。不能因为使用了授权码，就省略这些规则。R2

6.7 授权码和访问令牌为什么不是同一个东西

数据 接收它的主要服务 可以做什么 被截获后要关注什么
授权码 T 认证中心的令牌端点 满足协议条件时，一次性兑换后续令牌 防止未被授权的兑换者成功使用
Access Token OA 日程 API 在有效期和授权范围内访问资源 防止泄露、重放和越权使用

只有“短期、一次性”还不够。若任何人拿着 T 都能无条件兑换，它就缺少关键的兑换约束。

授权码流程主要保护取得令牌的过程。真正的持有者访问令牌如果随后从后端泄露，攻击者仍可能使用它；后端保存、传输和 API 校验仍然重要。公开客户端不能可靠保管秘密，需采用适合它的绑定机制；不能把本例的后端秘密写进前端。

6.8 为什么签名或加密不能单独代替这些交付规则

签名让 API 确认令牌来自可信签发者、内容未被改动，但不自动证明发送令牌的人就是最初得到它的应用。

加密能隐藏内容，但要区分两种使用方式。如果 API 直接接受加密后的令牌 E，攻击者拿到 E 后可能原样提交，无需先解密。若将真正令牌包装后只加密给指定应用后端，只有后端能解密取出令牌，则可以保护交付，但需要相应的密钥和协议设计。

因此，签名、加密和授权码不是三个互相替代的版本。它们分别涉及来源和完整性、内容保密，以及带条件的凭证交付。是否组合使用取决于协议和需求；“加密后就不会被冒用”也不是通用结论。R11R16

6.9 授权服务器与业务权限判断并不重复

scope⁴⁴ 可以按平台约定表达访问范围，例如 calendar.read。这个名称只是本例约定，不是所有 OAuth 平台都内置的标准 scope。

平台可以签发“允许读日程”的令牌；OA 仍需检查令牌是否面向自己、是否允许当前操作，以及目标日程是否属于被授权访问的资源。

把 userId=别人 放进 API 参数，不应该绕过数据权限。令牌里的范围与业务资源权限要共同检查。

用户授权不一定每次弹确认框，是否交互确认还取决于既有授权、管理员同意和组织策略。

本阶段回顾

基础 SSO 已在第 3～5 节完成。本节先引入受限 API 访问需求，再发现访问令牌的交付风险，最后选择授权码加后端兑换来处理。OAuth 2.0 是组织这些授权交互的框架；认证中心与授权服务器可以是同一平台承担的不同职责。

7. API 越来越多：为什么有时会选择 JWT

第 6 节已经用 OAuth 2.0 说明了日程助手怎样申请权限、取得访问令牌，并用令牌调用 OA。接下来保持这套交互不变，只继续追问：这份访问令牌具体长什么样，OA 怎样验证它？

7.1 先别假设 Access Token 一定是 JWT

上一步签发的 Access Token⁴⁵ 完全可以只是一个随机字符串：

OA 收到这个令牌后，可通过受保护的 introspection⁴⁶ 接口向授权服务器查询它是否有效及相关元数据。这种令牌对 OA 表现为不透明令牌。OA 不能仅从这个随机字符串中读出身份和权限。R7

7.2 新问题：每次都查询中心有成本

如果大量 API 请求都远程查询，可能增加延迟、中心负载与可用性依赖。缓存可以减少请求，但缓存期间的撤销和权限变更又会有延迟。

一种选择是让令牌携带可验证的声明，由 API 使用可信公钥本地验证。JWT³⁶ 是可以采用的格式之一。这里先讨论常见的签名形式。

这只是说明一个常见的采用动机。JWT 并不是为这一家公司发明，也不是只有这一种用途。

因此，JWT 中只放完成目的所需、允许接收方看到的信息，不放密码或其他秘密。用户标识也可能涉及隐私。即使内容不敏感，访问令牌本身仍是凭证，被复制后可能被使用。需要隐藏内容时，可以评估加密形式或不透明令牌；HTTPS 则保护网络传输。

OA 事先配置可信签发方、允许的算法和可信公钥来源。收到 JWT 后，OA 根据允许列表检查算法，再根据 kid 从可信公钥集合中选择候选公钥，验证 Header 与 Payload 对应的签名。OA 不能因为令牌提供了某个陌生密钥地址，就无条件相信并使用它。

这里的“本地验证”指验签时不必逐个令牌询问中心。OA 首次获取公钥、遇到密钥轮换时仍可能需要从可信来源更新缓存。JWT 安全最佳实践

字段或约束 要回答的问题

7.4 本地验证带来了什么代价

假设令牌还有 5 分钟到期，小林现在撤销日程助手的授权。OA 如果只验签与检查时间，不查最新状态，就可能仍接受这个令牌。

因此 JWT 需要配合短有效期、撤销记录、账号状态查询或事件通知等策略。要求更及时地撤销，就要承担相应的状态和通信成本。

方式 优势 需要面对的问题
不透明令牌加在线查询 集中检查当前状态较直接 查询成本、中心依赖、缓存窗口
自包含 JWT 加本地验证 减少逐请求远程查询 撤销与权限变化、密钥轮换、声明验证

7.5 三个不能混淆的结论

  1. 回看第 6 节，OAuth 2.0 规定日程助手怎样申请授权和取得令牌；本节的 JWT 则回答令牌中的声明怎样表达和验证。同一套 OAuth 2.0 流程可以使用不透明令牌，也可以使用 JWT，二者不是互相替代的协议。
  2. JWT 的签名通常不隐藏内容，Base64URL 解码即可看到常见签名 JWT 的载荷。
  3. SAML 与 JWT 不构成“旧协议升级为新协议”的关系。SAML 常用 XML 身份声明，JWT 可用于不同协议与场景；不能把替换数据格式当作完成了协议迁移。

现代 Web、移动应用和 API 场景促使团队重视 HTTP/JSON 生态与轻量接入，但“REST⁵⁰ 兴起，所以 JWT 取代 SAML”不是准确的因果链。

8. 新增“用公司账号登录日程助手”：引入 OIDC

8.1 先区分两个需求：允许读日程，与登录日程助手

第 6～7 节解决的是：小林允许日程助手读取自己的 OA 日程，助手后端取得 Access Token，再携带它调用 OA API。这个功能叫“连接 OA 日程”，并不自动等于小林已经登录了日程助手自己的账号。

现在日程助手增加另一个入口：“使用公司账号登录日程助手”。它不想再让小林注册一套独立密码，而是希望信任公司身份平台的认证，找到对应的助手账号，并创建日程助手自己的本地会话。

功能 日程助手需要得到什么 得到之后做什么
连接 OA 日程 允许访问 OA 日程 API 的 Access Token 在后端调用 OA，读取获准访问的日程
使用公司账号登录助手 能可靠确认“小林是谁、她已完成适用认证”的登录凭证 对应到助手自己的用户记录，建立助手本地会话

本节里的“用户”一直指小林；“客户端”指申请授权或发起登录的日程助手；“资源服务器”指 OA 日程 API。OA API 是被调用方，不是这次登录流程中的客户端。

这里没有要求“小林每次使用 Access Token 时再登录一次”。调用 OA API 仍按前面的令牌与权限规则处理。我们新增的是让小林进入日程助手自己账号的登录功能。

8.2 为什么需要标准身份规则，以及 OIDC 怎样补上

小林可能已经在公司身份平台登录过，但日程助手仍需要获得面向自己的可信身份说明，才能建立助手的本地会话。这与前面 OA 信任中心登录凭证后建立本地会话的思想相同。

日程助手可能想：“我已经拿到 Access Token，能不能直接把它当作小林登录助手的凭证？”

前面的 Access Token 用于日程助手访问 OA 日程 API，OAuth 2.0 解决的是小林允许助手访问哪些资源的问题。

OIDC 解决的是另一个明确问题：

日程助手要让小林“使用公司账号登录助手”，怎样获得并验证小林的身份认证结果？

这不等于 Access Token 永远不包含用户标识，也不等于 OA API 无法知道授权用户是谁。OA 可以按约定从令牌或查询结果中识别小林，并检查日程权限；这里缺少的是日程助手用来完成用户登录的一套标准身份认证规则。

如果助手调用提供方自定义的用户接口来实现登录，还需要遵守提供方额外规定的身份与安全语义。为了让不同应用按统一规则接入，我们引入 OIDC。

从日程助手的需求，回到官方定义

上面的例子说明了我们想做什么。现在再看规范，里面的“客户端”“最终用户”“身份层”就可以对应到已经认识的参与方和功能。

OIDC⁵² 全称 OpenID Connect。依据《OpenID Connect Core 1.0》摘要与第 1 节，其定义可以转述为：

OpenID Connect 是构建在 OAuth 2.0 之上的身份层。它让客户端依据授权服务器完成的认证来验证最终用户的身份，并以可互操作的方式获取用户的基本资料。

以上是官方定义的中文转述，不是逐字引文；正式表述和规则以规范为准。R1R17

把定义中的表述放回本例：

定义中的表述 在本例中是什么意思
OAuth 2.0 之上的身份层 沿用前面已经认识的请求、授权码与换令牌流程，再增加面向用户登录的标准身份结果及规则
客户端验证最终用户的身份 日程助手确认“小林是谁、她已完成适用认证”；最终用户是小林，客户端是日程助手
依据授权服务器完成的认证 公司身份平台负责认证小林，助手按规则验证平台交付的结果，不需要拿到小林的公司密码
可互操作地获取基本资料 平台和应用遵守共同的消息、字段含义与处理规则；不必每次都重新约定用户标识、姓名、邮箱等如何表达

这里的“身份层”不表示又增加一台服务器，而是给原有授权交互补充身份认证方面的标准规则。

标准具体约定了什么

仅说“返回一个表示用户身份的令牌”还不够。平台和助手还需要对请求、消息内容、交付方式和验证步骤达成一致：

约定的部分 规则要点 日程助手怎样使用
如何发起认证 OIDC 请求必须包含 openid scope，并符合所选流程的参数规则 明确请求用户认证，而不只是申请某个 API 的访问权限
ID Token 表达什么 使用标准声明，必需项包括签发者 iss、主体 sub、受众 aud、到期时间 exp 和签发时间 iat 知道谁签发、对应谁、发给谁，以及相关时间条件
结果怎样交付 按所选 OIDC 流程交付结果；本篇采用授权码流程，由后端兑换取得令牌 按约定处理响应，不自行发明回调字段和兑换语义
结果怎样验证 按流程检查签名、可信签发者、预期受众、时间及适用的请求关联；请求发送了 nonce 时，要检查对应返回值 确认结果可以用于当前助手的这次登录，而不只是解码查看姓名
用户资料怎样表达与取得 规范定义姓名、邮箱等声明及相应获取方式，具体返回受请求、授权和平台策略限制 按标准语义处理资料；不假设每次登录都一定返回所有字段

这张表是学习提纲，不是完整的合规检查清单。具体实现还要遵守所选流程和平台的全部适用要求。R1R18

因此，OIDC 的重点是：应用按标准流程取得并验证标准化的用户认证结果。ID Token 是承载这个结果的核心凭证，但不是 OIDC 的全部。

例如，一个自定义接口返回包含小林姓名、邮箱的 JWT，并把字段命名为 id_token，并不自动说明它符合 OIDC。还要看请求、令牌语义、签发、交付和验证是否符合相应规则。

再对应到日程助手的登录

日程助手请求 openid scope，按约定获得 ID Token⁵³，验证后用它确认小林的认证结果，再关联助手自己的账号并建立本地会话。后面第 8.3、8.4 节会继续展开这份结果与 Access Token 的分工，以及一次完整登录。

这里依然可以使用原来的统一身份平台。

已有参与方 在这次 OIDC 登录中的职责 协议名称
小林 用公司身份登录日程助手的人 用户
公司身份平台 认证小林，签发登录结果 OP⁵⁴，身份提供方
日程助手 发起登录，接收并验证小林的登录凭证 RP，也是这次交互中的 OAuth Client
OA 日程 API 接收助手携带 Access Token 的资源访问调用 Resource Server，资源服务器

SAML 里常说 IdP、SP，OIDC 里常说 OP、RP。这些是对应协议中的角色名，不表示多了四个服务器。

8.3 ID Token 与 Access Token 分工

先对应已有概念：第 6 节记为 T 的临时授权码，在协议中的参数名是 code，它仍然是用于兑换的中间凭证。OIDC 在后续返回的数据中增加 ID Token，用来承载前面基础 SSO 所关心的用户身份和认证信息。

为了与还需要兑换的 code 区分，从这里把可用于确认用户认证情况的数据称为“最终认证结果”。ID Token 承载这种结果，助手仍必须按协议验证它；Access Token 则用于 API 访问，不等于最终身份认证结果。

这不是给第 3～5 节补上一层必需步骤，而是将已理解的授权码交付流程用于 OIDC 登录，并明确两种令牌的用途。

凭证 本例中谁使用它 用来判断什么
ID Token 日程助手后端 这次登录的小林是谁，结果是否来自可信平台、面向本助手且满足本次登录要求
Access Token 获得授权的资源 API，本例可包括 OA 日程 API 本次资源访问是否具有有效授权，并符合 API 的业务权限

ID Token 的受众通常是日程助手的 client ID⁵⁵；Access Token 应面向约定的资源 API。不能用 ID Token 代替 Access Token 调用任意业务接口。

OIDC 的 ID Token 使用 JWT 格式；Access Token 可以是 JWT，也可以是不透明字符串。JWT 帮助表达声明，但它本身没有定义完整登录流程。

8.4 在日程助手上完成一次登录，不等于登录两遍

本例假设平台支持日程助手的公司账号登录，以及相应的 OA 日程访问授权。不是任意 OIDC 流程返回的 Access Token 都能访问 OA，它还需要面向正确的 API，并具有所需授权。

同一次认证与授权流程可以同时满足登录和资源访问需求，不必为了这两种令牌各让小林输入一次密码。若小林在中心已有符合要求的会话，新的助手登录流程也可能无需再次输入密码。

“日程助手验证 ID Token”的具体意思是：助手后端按 OIDC 规则检查签名、可信签发者、面向自己的受众、有效期、本次请求关联等，确认结果可用于建立这次助手会话。它不表示 OA API 要求用户在每次令牌调用时重新打开登录页面。R1

8.5 换回 OA 的 SSO 时，OA 才是登录客户端

上面讨论的是“小林登录日程助手”。现在明确换回第 3 节的场景：“小林登录 OA”。在这次交互中，OA 发起 OIDC 登录、接收 ID Token 并建立自己的会话，因此 OA 是登录客户端。

同一个系统可以承担不同角色，角色取决于正在讨论的交互：提供日程 API 时，OA 是资源服务器；让小林登录 OA 网站时，OA 又可以是 OIDC 客户端。不能把这两次交互混成一个角色。

我们可以选择 OIDC 作为 OA、CRM 与认证中心之间的协议，代替自定义协议或采用另一种现有接入方式。

如果 OA 只需要用户登录，不需要调用额外 API，就不必为了演示令牌种类而强行设计更多资源服务。

CRM 使用相同平台登录时，复用符合要求的中心会话，再取得面向 CRM 的登录结果并建立本地会话。这仍然是第 3 节的 SSO 思想，只是使用了 OIDC 标准。

8.6 本阶段回顾与实际选型顺序

本节先新增“小林登录日程助手”的需求，用 OIDC 规定助手怎样取得并验证用户认证结果，再明确切换回“小林登录 OA”的场景。API 访问和应用登录是两个功能，可以在一次适当的流程中同时满足，不等于让用户重复登录。

本文先介绍企业 SSO，再讨论第三方授权，最后介绍 OIDC，是为了沿问题展开。实际系统可以从一开始就用 OIDC 建统一登录，也可以单独使用 OAuth 做 API 委托授权，不需要按本文顺序逐级升级。

本篇名词注释

¹ OA，Office Automation，办公自动化。本文指内部办公系统，常用于请假、报销、审批、公告和日程。

² CRM，Customer Relationship Management，客户关系管理。本文指记录客户资料、联系记录、销售跟进和商机的系统，例如记录某位客户的需求与下次跟进时间。

²⁸ Client，客户端。在这里指接入某种服务或协议的应用，例如接入 CAS 的 OA；OAuth 中则指申请访问授权的应用，不一定是浏览器。

³⁰ API，Application Programming Interface，应用程序编程接口。本文通常指后端供程序调用的入口，例如查询小林日程的接口。

³⁶ JWT：JSON Web Token。声明格式，可用于表达令牌，不是完整登录协议。

³⁷ OAuth 2.0：开放授权框架。应用申请受限的资源访问能力。

³⁸ Session：会话。应用维持登录状态。

³⁹ Access Token：访问令牌。给 API 验证访问授权。

⁴⁰ Resource Server：资源服务器。提供受保护的 API。

⁴¹ 后通道指服务端之间直接通信，前通道指通过浏览器转交消息。

⁴² 授权码是用于兑换令牌的短期一次性中间凭证。它不是用于长期调用业务接口的访问令牌。

⁴³ PKCE：Proof Key for Code Exchange。把授权码兑换绑定到持有 verifier 的客户端事务。

⁴⁴ scope：授权范围。表达允许读取日程等能力。

⁴⁵ Token：令牌、凭证。按其类型证明访问能力或表达认证结果。

⁴⁶ introspection：令牌内省、状态查询。向授权服务器询问令牌是否有效。

⁴⁷ JWS：JSON Web Signature。JSON 数据的签名表示规范。

⁴⁸ Base64URL：适合 URL 等场景的文本编码。编码可还原，不提供加密保密性。

⁴⁹ 租户：需要隔离数据和权限的客户组织。同一 CRM 中的甲公司和乙公司。

⁵⁰ REST / RESTful：网络服务的架构风格 / 遵循该风格。用资源与统一接口组织服务。

⁵² OIDC：OpenID Connect。在 OAuth 2.0 上增加标准身份认证层。

⁵³ ID Token：身份令牌。给 OIDC 客户端确认认证结果。

⁵⁴ OP / RP：OpenID Provider / Relying Party。OIDC 中的身份提供方 / 依赖身份结果的应用。

⁵⁵ client_id 是应用的注册标识，通常不需要保密。client_secret 是按所选认证方式使用的应用秘密凭据，必须保密，不能放在前端代码中。

⁹⁰ RFC 是互联网技术规范等文档的编号体系，并非所有 RFC 都是标准；W3C 是制定 Web 技术规范的组织；OWASP 是提供应用安全资料和项目的开放社区。
