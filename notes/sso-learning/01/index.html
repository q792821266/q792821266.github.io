从单个 OA 开始，跟着小林理解 Cookie、会话、统一账号、跨域 SSO、签名凭证与 SAML。

小林是公司员工。OA¹ 是办公系统，CRM² 是客户管理系统。小林通过浏览器⁴访问应用，应用的服务端⁵处理请求。两个应用沿用同一家公司的例子。

1. 只有一个 OA：先解决“怎么登录”和“怎么记住”

1.1 现状：OA 自己管理账号密码

公司只有一个 OA 系统，用来查看公告、提交报销和管理日程。此时只有三个参与方：

小林输入用户名和密码，浏览器通过 HTTPS⁶ 把凭据⁷交给 OA。OA 找到用户记录，验证密码。

数据库⁸保存密码散列⁹等验证数据，不应保存明文密码。

这里不需要另一个认证服务器¹⁰。OA 自己就完成了身份认证。

“身份认证”回答的是：提交请求的人，能否证明自己就是小林？密码是这种证明的一种。

1.2 新问题：下一次请求还要输入密码吗

小林登录后打开“我的日程”，接着打开“我的报销”。HTTP¹¹ 不会自动把两次请求识别成同一个已登录用户。

如果每次都提交账号密码，体验差，也会让长期凭据反复经过业务接口。

1.3 方案：登录后创建会话

OA 验证密码成功后，生成一个难以猜测的随机会话标识，例如 session_id。OA 在服务端保存它与用户的对应关系，再让浏览器通过 Cookie¹² 保存这个标识。

之后浏览器访问 OA 时，按 Cookie 规则带上 oa_session=A。OA 查会话库，就能把请求识别为小林的已登录请求。

这里的 Cookie 装的是 Session ID¹³，OA 通过它找到服务端的会话状态。图中的 Set-Cookie 用于要求浏览器保存 Cookie。

用户数据库和会话库可以部署在同一数据库中，也可以分开。图上分开讲职责，不代表必须增加服务器。

“会话”是逻辑概念，Session 是它的英文名称

会话表示系统把一系列请求关联起来，视为一段持续交互的上下文。例如，把“打开公告”“查看日程”“提交报销”都关联到小林的同一段登录状态。

在本文采用的服务端会话方案中，OA 在服务端保存一条记录，浏览器只通过 Cookie 保存用来找到记录的标识：

因此，“会话”“服务端的会话记录”和“Cookie 中的会话标识”相互配合，但不是同一个东西。框架里的 Session 对象是对会话状态的一种具体管理方式；其他架构也可能用不同方式承载会话。

“浏览器的 session”容易混指下面几件不同的事：

名称 指什么 是否等于 OA 服务端的会话
浏览器使用会话 从打开到结束浏览器的一段使用过程，是较宽泛的说法 不等于，结束时间也不必一致
Session Cookie，会话 Cookie 没有显式持久过期时间、生命周期通常由浏览器会话决定的 Cookie 不等于，它只是 Cookie 的一种；可以用来携带会话标识
sessionStorage 网页脚本使用的浏览器存储，按来源和标签页等维度隔离 不等于，里面的数据不会像 Cookie 那样自动放入 HTTP 请求

同一个浏览器中的两个普通标签页，通常可以共享适用的登录 Cookie，但不等于共享同一份 sessionStorage。此外，浏览器的会话恢复功能可能恢复会话 Cookie，所以不能把“关掉浏览器”当成可靠的服务端退出操作。R13R14

1.4 登录成功，还需要检查权限

小林可以提交自己的报销，但未必可以审批别人的报销。因此，第一版 OA 就需要两种判断：

判断 在 OA 中的例子 名称
请求是谁发的 通过会话识别为小林 身份认证 AuthN¹⁴
这个人能否做这件事 小林是否有权审批这张报销单 授权或访问控制 AuthZ¹⁵

授权从单应用阶段就存在，不需要等到引入“授权服务器”才出现。 普通业务授权通常由 OA 自己完成。

本阶段回顾

只有 OA。OA 既验证密码，也管理会话，还检查业务权限，这个阶段不需要另外的认证中心。

2. 增加一个 CRM：先把账号管理统一起来

2.1 现状：每个系统都有自己的账号

公司上线 CRM，小林需要分别注册并登录两个系统。

员工入职要开通两份账号，改密码可能改两次，离职也可能漏停其中一个系统。系统越多，问题越严重。

2.2 方案：统一用户目录

把员工账号集中管理，OA 和 CRM 都使用同一套身份数据。它可以由用户服务提供接口，也可以采用 LDAP¹⁶ 等目录服务。

生产系统不一定允许所有应用直接读用户表。可以通过受保护的接口或目录认证能力对接，控制密码验证和数据访问权限。

现在入职、改密码、停用账号可以集中管理。这解决了账号来源重复的问题。

2.3 还没解决：每个应用仍然要登录

小林登录 OA 后，CRM 不知道这件事。CRM 仍然没有自己的登录会话，所以还会展示登录框。

即使小林在两个系统输入的是同一个账号密码，也还没有实现“登录一次，多个系统复用”的单点登录，也就是 SSO¹⁷。

已经统一的东西 仍然独立的东西
账号来源、密码管理、账号状态 各应用的登录过程与会话

本阶段回顾

统一账号解决“到哪里管理用户”。接下来要解决“能不能复用已经完成的登录”。

3. 不想反复输密码：引入统一认证中心

3.1 为什么需要这个新角色

如果 OA、CRM 都自己验证密码，就很难知道用户是否刚在另一个系统完成认证。

我们把“验证用户身份，并记住用户已完成认证”这件事集中到一个独立的逻辑组件，叫它“统一认证中心”。

为了先看清各方怎样配合，我们把认证中心提供给业务系统、用于完成登录的数据统称为“登录凭证”。这是教学上的占位词。本节先沿用这个名字，到第 4 节选择带签名的登录凭证，把基本 SSO 讲完整；具体协议名称稍后再对应。

认证中心可以使用上一节的统一用户目录。目录负责用户数据，认证中心负责登录过程，两种职责可以在一个产品中实现。

这是从现有系统中提取职责，不是在文章里凭空增加一种服务器。

3.2 先看完整访问过程

本节一直沿用“登录凭证”这个统称，先理解它怎样帮助业务系统完成登录。这里的登录凭证，与浏览器访问认证中心时使用的中心 Cookie、登录业务系统后使用的本地 Cookie，分别承担不同用途。

首次访问 OA，先假设当前浏览器没有有效的 OA 登录状态，也没有可复用的中心登录状态：

  1. 小林访问 OA，OA 发现没有有效本地会话。
  2. OA 把浏览器跳转到认证中心。
  3. 小林在认证中心输入密码，必要时完成第二因素认证。
  4. 认证中心建立自己的中心会话，让浏览器保存对应的中心 Cookie，再让浏览器带着面向 OA 的登录凭证回到 OA。
  5. OA 验证登录凭证，识别小林，创建自己的本地会话。
  6. 小林进入 OA。

随后访问 CRM，需要分别检查 CRM 的本地状态和认证中心的登录状态，不能从其中一种状态推断另一种：

  1. CRM 检查当前浏览器是否对应一个有效的 CRM 本地会话。有则按应用策略继续访问；没有则让浏览器跳转到认证中心。
  2. 浏览器请求认证中心，按照 Cookie 规则决定是否附带已有的中心 Cookie。跳转本身不会凭空生成一份中心 Cookie。
  3. 认证中心根据请求分情况处理。如果收到有效的中心 Cookie，并找到仍然有效且满足本次认证要求的中心会话，通常可以复用认证；如果没有收到 Cookie、找不到有效会话或需要更强验证，就要求用户完成相应认证。
  4. 认证中心在认证条件满足后，为 CRM 生成登录凭证，浏览器把它带回 CRM。
  5. CRM 验证登录凭证并检查应用准入条件，然后创建 CRM 本地会话，小林进入 CRM。
当前访问所对应的状态 接下来发生什么
CRM 本地会话有效 通常直接访问 CRM，不必为了每次请求都跳转中心
CRM 无有效本地会话，但浏览器能携带有效中心 Cookie，且中心会话满足要求 跳转中心后复用认证，通常无需再次输入密码
CRM 无有效本地会话，浏览器也没有可用的中心 Cookie，或中心会话失效 跳转中心后重新认证，再建立 CRM 会话

“登录 OA 后访问 CRM，无需再次输入密码”的例子，假设小林使用同一设备上的同一浏览器配置，而且中心 Cookie 可以发送、中心会话仍有效并满足要求。换设备、换浏览器、进入独立无痕环境或清除 Cookie 后，不能直接套用这个假设。新环境如果此前也已完成中心登录，则可能复用新环境自己的中心会话。

这就是单点登录：在可以复用认证的环境与策略范围内，用户完成一次交互式认证后，就能进入多个应用。它不保证用户在任意设备或浏览器中都自动继承原来的登录状态。

“无需再次输入密码”不等于“没有再次跳转”。第二个应用仍可能经过一次非常快的协议流程。

3.3 三份会话分别放在哪里

假设地址为：

会话 浏览器向谁发送对应 Cookie 服务端保存什么 用途
中心会话 C 认证中心 C 对应小林，认证时间与过期状态 判断是否需要再让用户输密码
OA 会话 A OA A 对应小林的 OA 登录状态 持续访问 OA
CRM 会话 B CRM B 对应小林的 CRM 登录状态 持续访问 CRM

认证中心会话解决“能否复用已经完成的认证”。OA 和 CRM 各自的会话解决“当前浏览器能否持续使用本应用”，应用可以设置自己的有效期、准入和退出策略。应用会话是常见设计选择，不代表物理上必须使用不同的数据库。

这里的“认证中心 Cookie”指认证中心让浏览器保存、供浏览器后续访问认证中心时使用的一份 Cookie。Cookie 保存在浏览器中，里面通常是识别中心会话的随机标识；认证中心服务端保存对应的登录状态。

在本例中，三个系统的域名不同。浏览器按每份 Cookie 的适用范围决定是否随请求发送，不会把认证中心的 Cookie 交给 OA 或 CRM。

下面沿用“小林在同一浏览器配置中登录 OA，接着访问 CRM，且中心 Cookie 和中心会话仍有效”的情况：

  1. 浏览器请求 CRM。浏览器不会附带认证中心的 Cookie，CRM 因而不能直接用这份 Cookie 识别小林。
  2. CRM 发现没有自己的有效会话，返回重定向响应，让浏览器访问认证中心的登录地址。
  3. 浏览器按照响应，向认证中心发起一个新的请求。这个请求的目标是认证中心，因此浏览器按 Cookie 规则，自动附带此前为认证中心保存的 Cookie。
  4. 认证中心收到请求，从 Cookie 中读出中心会话标识，查到小林已有有效登录状态，因此通常无需再次要求密码。
  5. 认证中心通过登录协议向 CRM 提供登录凭证。CRM 验证登录凭证后，建立自己的本地会话。

所以，“把中心 Cookie 发给中心”的完整意思是：浏览器向认证中心发送请求时，把此前保存的认证中心 Cookie 附在这个请求中。CRM 获得的是前文所说的登录凭证，不是这份 Cookie。

谁返回跳转地址，Cookie 又怎样跟着请求发送

在这一步，返回跳转地址的是 CRM。CRM 的配置中已经知道认证中心的地址，不需要先等认证中心返回地址。CRM 可以给浏览器返回如下响应，让浏览器改为访问认证中心。R15

这里的地址只用于说明跳转，省略了实际登录协议要求的其他参数。响应中的 Location 是目标地址，地址本身没有包含认证中心 Cookie。

浏览器随后自动发起一个新的请求。如果此前已经为认证中心保存了 idp_session=C，而且 Cookie 的域名、路径、安全和跨站发送规则等条件允许，浏览器会把它放在这个新请求的 Cookie 请求头中。R13

这就是“自动附带”：浏览器自身管理 Cookie 存储，并在发送请求时检查哪些 Cookie 可以随请求发送。CRM 不需要、也不能因为返回了一个跳转地址就读取认证中心的 Cookie；网页脚本也不需要手工拼接这份 Cookie。Cookie 不会因此出现在地址栏。

换浏览器，还能免登录吗

小林如果在 Chrome 中登录了认证中心，通常只有 Chrome 当前使用的浏览器配置保存了对应 Cookie。换到 Edge、另一份浏览器配置或独立的无痕环境，通常不能复用原来的中心 Cookie。

认证中心服务端可能仍保留原来的登录会话，但新浏览器没有原来的标识，无法仅凭旧浏览器的那份状态证明自己已登录。因此，新浏览器通常需要完成一次认证，建立自己的中心会话。之后，新浏览器中访问 OA、CRM 等应用时，又可以复用这次认证。

这表示原有登录状态没有自动跨浏览器共享，并不表示新浏览器不能使用 SSO。企业设备认证等其他机制也可能让新浏览器无需手工输入密码，但那需要额外的身份凭据和策略支持。

因此跨域 SSO 可以成立，不需要让所有系统共享 Cookie。把 Cookie 的 Domain¹⁸ 扩大到同一父域只是特定部署方案，还会扩大相互信任范围。

3.4 认证中心与身份提供方是同一个东西吗

在这条流程中，认证中心向 OA、CRM 提供可信身份，所以也可以称为身份提供方 IdP¹⁹。

“认证中心”是便于理解的架构名称，“IdP”是强调身份提供职责的角色名称。到这里，系统中仍然只有我们刚引入的那个中心。

后文遇到协议专用名字时，会先说明它对应谁，不默认读者已经认识它。

本阶段回顾

统一认证中心解决重复交互式登录。中心会话用来复用认证，应用会话用来持续访问应用，二者不是同一份状态。

4. OA 怎样验证登录凭证：先把基础 SSO 讲完整

4.1 新问题：浏览器转达的消息可以被修改

认证中心如果只把浏览器跳转到下面的地址，OA 就凭用户编号让人登录，会有什么问题？

攻击者可能自己构造这个 URL²⁰，冒充小林。因此，“URL 中有用户编号”不构成可信证明。

OA 需要确认：登录凭证是不是可信中心发的，内容有没有被改，是不是发给 OA，是否属于当前登录过程，以及现在是否仍可使用。

4.2 方案：认证中心签名，OA 验证

先选择一条能够完成基础 SSO 的路径：认证中心把身份信息和使用条件写进登录凭证，并附上数字签名。浏览器负责转交，OA 负责验证。

可以把登录凭证的内容简化理解为：

认证中心保密持有签名私钥。OA 事先配置可信公钥²²，用它检查签名。浏览器修改了受签名保护的内容，就无法通过正确的验证。只有公钥的 OA 可以验签，但不能因此冒充中心签发登录凭证。

OA 还要检查接收应用、有效时间，以及与本次登录事务²³的关联。签名有效并不代表任意应用、任意时间都能使用这份登录凭证。

到这里，第 3 节的“登录凭证”有了一个具体实现：带数字签名的身份说明。我们继续沿用“登录凭证”，不用再为同一步骤更换名称。

4.3 把签发、验证和本地会话连起来

回调²¹入口是 OA 接收这次登录凭证的地址。在这条路径中，OA 使用事先信任的公钥和本次请求上下文完成登录凭证的验证。

为什么凭证经过浏览器回到 OA？ 这次访问认证中心的请求来自浏览器，中心的响应也返回给浏览器。中心已经知道并按协议检查 OA 的回调地址，让浏览器把凭证提交到这个地址，OA 就能把结果关联到该浏览器发起的登录，并在响应中设置 OA Cookie。

认证中心与 OA 也可以使用协议支持的服务端通信，但服务端之间的一次响应，不会自动把 Cookie 设置到小林的浏览器。浏览器和 OA 如何继续关联这次登录，仍需要单独处理。

在本节的方案中，OA 验证登录凭证后通常不必长期保存完整凭证；它保存本地会话，浏览器携带会话标识。为了防止同一凭证再次用于登录，OA 仍可能按协议短期记录凭证的唯一标识。

小林接着访问 CRM 时重复同一条流程，但中心签发的是面向 CRM 的登录凭证。中心能否免去再次输入密码，仍取决于当前浏览器是否携带可用的中心 Cookie，以及中心会话是否满足要求。

4.4 这条路径需要哪些安全条件

OA 应通过成熟框架完成协议验证，不能自己拼接一份带姓名的 JSON 就当作可信登录凭证。需要验证的内容包括签发来源、签名、接收应用、有效期、请求关联和适用的重放²⁴防护。

数字签名保护来源和内容完整性，通常不隐藏内容。浏览器参与传递登录凭证，需要 HTTPS 和严格的接收、验证规则。如果有额外的内容保密要求，可以采用协议支持的加密能力。

加密和签名的职责不同，加密也不能单独保证凭证不被复制使用。后面讨论访问令牌交付时，再结合具体风险展开，不在基础 SSO 中预先增加新的凭证阶段。

4.5 本阶段回顾：基础 SSO 已经形成闭环

这条路径已经能实现前面的目标：OA、CRM 复用中心认证，各自建立会话。后面的新机制需要由新问题来引出，而不是基础 SSO 必须依次增加的步骤。

5. 接入系统越来越多：用标准协议代替自定义约定

5.1 新问题：每个团队都定义一种登录格式

OA 团队用 user_id 表示用户，CRM 团队用 employee_id；两个团队对签名覆盖哪些内容、接收地址如何检查，也有不同约定。每接一个系统，都要重新解释字段、验证规则、错误处理和退出行为。

因此需要共同遵守的协议。我们先用 SAML²⁷ 把上一节的签名凭证流程标准化，继续沿同一条主线理解。

5.2 SAML 2.0：给已有参与方和登录凭证约定标准名称

使用 SAML 时，同一批参与方的名称如下：

原来的参与方或数据 SAML 名称 对应的职责
认证中心 IdP，身份提供方 认证用户并签发登录凭证
OA、CRM SP，服务提供方 验证登录凭证并提供业务服务
登录凭证中的身份声明 Assertion 表达用户身份、认证情况和适用条件
传递身份声明的响应消息 SAML Response 将身份声明按协议交给业务系统

这里没有多出新的服务器。Assertion 是原来登录凭证中身份声明的协议名称；SAML Response 是传递它的消息名称。

5.3 按标准完成同一条登录流程

常见 SP 发起的 Web³¹ SSO 流程为：

OA 接收 SAML 响应的端点³²常称 ACS³³，就是这个协议的回调接收地址。

SAML 使用 XML²⁵ 表达数据。Assertion 可以包含用户标识、认证时间和部门等属性。SAML metadata³⁴ 用于交换实体标识、端点和签名证书³⁵等配置。

OA 必须确保使用的身份内容确实处于有效签名的保护范围内，再检查受众、时间、请求关联等规则。不要自己用字符串查找 XML 标签来完成验证，应使用维护良好的框架或库。R4

这里只介绍常见的浏览器转交签名声明的 SAML 流程，用来对应第 4 节。SAML 还支持其他传递方式，并非只有这一条路径。

5.4 到这里，基本 SSO 已经讲完整

第 3 节先用“登录凭证”统称中心提供给应用的登录数据；第 4 节选择签名方案解释可信来源；本节再把这套交互对应到 SAML 的身份声明和响应。

小林已经可以通过认证中心登录 OA、CRM，各业务系统验证登录凭证后，建立并管理自己的本地会话。

接下来公司接入第三方日程助手，出现的是“让应用获得受限的 API 访问能力”的新需求。下一节从这个新问题开始，不把后续机制当作基础 SSO 必备的层次。

本篇名词注释

¹ OA，Office Automation，办公自动化。本文指内部办公系统，常用于请假、报销、审批、公告和日程。

² CRM，Customer Relationship Management，客户关系管理。本文指记录客户资料、联系记录、销售跟进和商机的系统，例如记录某位客户的需求与下次跟进时间。

⁴ 浏览器是用户打开网页的程序，例如 Chrome、Edge。

⁵ 前端是在浏览器中展示页面、处理交互的部分；后端或服务端接收请求、查询数据并执行业务规则。

⁶ HTTPS 是通过 TLS 保护的 HTTP，用于保护浏览器与网站之间传输的数据。TLS，Transport Layer Security，即传输层安全协议，提供加密、完整性和适用的对端认证。HTTP 是浏览器和网站交换请求、响应的常用协议。

⁷ 凭据是用来证明身份或访问资格的数据。账号密码、会话标识和访问令牌属于不同场景的凭据。

⁸ 数据库用于组织和保存用户、日程等数据。图中的用户库和会话库表示不同职责，不要求分别部署服务器。

⁹ 密码散列是使用适合密码存储的算法计算出的验证数据。服务端按算法规则验证输入密码，不应保存明文密码，密码存储要求见第 4 篇的第 11 节。

¹⁰ 服务器指运行服务程序的计算机或计算资源。一个服务器可以运行多个服务，一个服务也可以部署在多台服务器上。

¹¹ HTTP，Hypertext Transfer Protocol，超文本传输协议，是浏览器和网站服务端交换请求、响应的常用协议。HTTPS 是通过 TLS 保护的 HTTP。

¹² Cookie：浏览器保存并按规则携带的数据。携带 OA 会话标识。

¹³ Session ID：会话标识。用于查找一段会话状态的随机值。

¹⁴ AuthN，Authentication，身份认证。确认请求者是谁。

¹⁵ AuthZ，Authorization，授权、访问控制。判断能否执行具体操作。

¹⁶ LDAP：Lightweight Directory Access Protocol。访问用户、部门、组等目录信息的协议。

¹⁷ SSO，Single Sign-On，单点登录。多应用复用一次认证。

¹⁸ Domain 是 Cookie 的适用域名范围属性。扩大其作用域会扩大相关应用之间的信任范围。

¹⁹ IdP / SP：Identity Provider / Service Provider。SAML 中的身份提供方 / 业务服务提供方。

²⁰ URL，Uniform Resource Locator，统一资源定位符，在这里可理解为网址。问号后通常是请求参数。

²¹ 回调：流程处理后返回结果的入口或动作。认证中心把浏览器送回 OA。

²² 在本文的非对称签名方案中，中心保密持有私钥用于签名，接收方持有可信公钥用于验签。只有公钥不能冒充中心生成有效签名。

²³ 登录事务在本文指一次登录的短期上下文，例如浏览器绑定、state、nonce、PKCE verifier；不是特指数据库事务。

²⁴ 重放：再次提交截获的有效消息或凭证。需要一次性规则、时限及适用的绑定机制。

²⁵ JSON / XML：两种文本数据格式。分别用键值等结构、标签等结构组织信息。

²⁷ SAML：Security Assertion Markup Language，安全断言标记语言。用标准身份声明支持跨系统信任。

³¹ Web：网页应用所处的技术环境。用户通过浏览器使用 OA。

³² 端点：接收特定请求的地址。登录入口、换令牌入口等。

³³ ACS：Assertion Consumer Service。SAML 中接收身份响应的端点。

³⁴ metadata：元数据、描述性配置。说明平台地址、能力、标识和证书等。

³⁵ 签名证书包含公钥等信息，用于双方约定的签名验证信任。SAML 签名证书与网站 HTTPS 证书是不同用途的配置。
