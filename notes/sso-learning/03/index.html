9. 把 OIDC 落地：一次登录的具体框架流程

本章沿用第 8.5 节“小林使用公司账号登录 OA”的场景。OA 在这里是发起 OIDC 登录的客户端，身份平台负责认证小林。第 6 节日程助手后端处理授权码的职责，在这次登录中由 OA 后端承担。

前面记为 T 的临时授权码，在协议中的参数名叫 code；两种写法指同一份凭证。OA 后端处理协议、保管本次登录的临时上下文和必要令牌；浏览器在登录成功后使用 OA Session Cookie。

9.1 部署上有哪些组件

发现配置⁵⁶与 JWKS⁵⁷ 由可信平台提供。端点是同一平台提供的不同 URL，不必每个端点部署一个服务。用户库、MFA⁵⁸ 等可以由身份平台管理或对接外部系统。

Spring Security、ASP.NET Core 的 OIDC 中间件⁵⁹等可处理协议接入。Keycloak 等产品可充当身份平台。它们属于不同层次：一个是业务应用中的安全框架，一个是提供身份能力的服务。

9.2 接入前先配置什么

  1. 在平台登记 OA，得到 client_id。
  2. 精确登记 OA 回调地址，例如 https://oa.example.net/auth/callback。
  3. OA 配置可信 issuer，使用受信任的发现配置定位协议端点和公钥。
  4. 配置适用的客户端认证方式，采用授权码流程，并启用框架提供的相应校验保护。下一节解释这些保护分别加在哪一步。
  5. OA 准备临时登录事务、本地会话、内部账号映射和权限规则。

有受保护后端的客户端可以保管客户端凭据，称为机密客户端。纯 SPA⁶⁰ 或安装在用户设备上的应用通常不能可靠保守 client_secret，称为公开客户端。把 secret 写在前端代码里不会改变客户端无法保密的事实。

9.3 展开“按协议验证”：先看三处需要核对的信息

第 6 节先说“助手满足兑换条件后取得令牌”，第 8 节先说“OA 验证 ID Token 后建立会话”。现在要实现它们，就需要把这些笼统的验证步骤展开。

先沿用原来的流程，不增加新服务器，也不要求小林多输入一次密码：

下面每次只补一个核对要求，先说明问题，再给它在协议中的名称。

回调真是这个浏览器刚发起的那次登录吗

OA 的 callback 地址可以被访问。OA 不能因为有人向这个地址提交了授权码，就直接为当前浏览器建立登录会话。缺少正确关联时，可能把别人发起的登录流程接到小林的浏览器上。

解决思路是：OA 发起登录时生成一个不可预测的随机值 S，保存它对应的本次登录上下文，并绑定发起登录的浏览器。浏览器跳到中心时带上 S，中心返回回调时原样带回 S。

OA 收到回调，检查返回的 S 是否属于当前浏览器发起且尚未消费的登录过程；检查通过后，按框架规则一次性消费这份上下文。

这个往返关联参数在协议中叫 state⁶³。

这里的浏览器绑定通常由框架的短期关联 Cookie 等机制完成。它是登录之前用于关联请求的状态，不等于登录成功后的 oa_session=A。只在全局存储中查到“存在这个 S”，却不检查对应浏览器和事务，并不够。R2

ID Token 签名是真的，就一定属于本次登录吗

签名有效能说明结果由可信平台签发、内容未被修改，但这一项本身不说明它就是 OA 当前这次登录所期望的结果。我们还希望把返回的身份信息与发起的认证请求对应起来。

OA 发起本次认证时再生成一个独立随机值 N，保存在同一份临时上下文中，并发送给中心。中心把 N 放进这次签发的 ID Token，OA 在按协议验证 ID Token 时核对是否与保存的 N 一致。

这个参数和 ID Token 中对应的声明都叫 nonce⁶⁴。

所以，state 在浏览器返回 callback 时用于关联和核对流程，nonce 则在 OA 验证 ID Token 时核对。它们有不同落点。请求中发送了 nonce，应用就必须按 OIDC 规则检查返回声明。R1

只有授权码 T，是否就足以兑换令牌

第 6 节已经说明，T 只是中间凭证，还要满足兑换条件。现在展开其中一种保护：为本次授权请求准备一份随机秘密 V，要求兑换者提供与本次请求匹配的 V。

OA 后端保管 V，在最初的授权请求中只发送由 V 计算出的摘要 H。中心记录 H 与相关请求、后续授权码的关联。后来 OA 后端兑换 T 时提交 V，中心按同样规则计算并比较 H。

这种机制叫 PKCE。它的两个协议参数名分别是 code_verifier 和 code_challenge：R3

本文记号 协议参数名 本例中谁保存、什么时候发送
V code_verifier OA 后端保存在本次登录上下文中，只在后端兑换 T 时发送给中心
H code_challenge OA 从 V 计算，在最初的浏览器授权请求中发送给中心

本文使用 S256⁶² 方式计算 H。符号只用来帮助阅读，真实值必须每次使用合规的高熵随机数据，不能把 S、N、V 等示意字母直接用作固定配置。

如果攻击者只截获 T，却没有本次 V，就不能满足这项兑换检查。客户端认证用于证明适用的应用身份；PKCE 则把兑换进一步关联到持有本次随机秘密的流程。机密客户端采用 PKCE，也仍应执行其注册方式要求的客户端认证。R2R3

把名称与原流程对齐

已经理解的流程位置 现在补上的具体核对 由谁检查
浏览器把 T 带到 OA callback state=S 是否对应当前浏览器的这次登录 OA 后端
OA 后端拿 T 向中心兑换 code_verifier=V 是否匹配最初记录的 H 认证中心
OA 收到并验证 ID Token 令牌中的 nonce=N 是否匹配本次保存值 OA 后端

这不是新增三份“已登录凭证”：state 是流程关联值，nonce 是认证结果关联值，PKCE 是兑换绑定机制。它们配合校验，并不替代用户认证、客户端认证或业务权限检查。

这些保护的目标有重叠。满足相应前提的 PKCE 或 OIDC nonce 也能提供协议层 CSRF⁶¹ 防护，不能机械地说每种机制只防一种攻击。本文选择明确保留这组关联与绑定，方便理解有后端的 OIDC 授权码流程；并非声称任何 OAuth 流程都一律强制使用这三个参数。R2

9.5 框架与业务代码怎样分工

函数名描述职责，不是某个框架可直接调用的 API。具体配置和回调钩子应按所用版本文档实现，不能用手工 Base64 解码代替完整 OIDC 验证。

外部身份通常按 (issuer, sub) 关联内部用户。不要只凭邮箱相同就自动合并账号；邮箱可能修改、回收，提供方的可信度也不同。使用 pairwise subject⁶⁹ 时，不同客户端拿到的 sub⁷⁰ 还可能不同，跨应用映射需要平台支持或明确规则。

适用于 HTTPS 顶层 GET 回调的本地会话 Cookie 示例：

Secure 限制安全传输；HttpOnly 限制脚本直接读取；__Host- 要求不设置 Domain 并使用 Path=/ 等条件。服务端仍要管理空闲超时与绝对超时。

如果使用 SAML 常见的跨站 POST 回调，或 OIDC form_post，Lax 的短期关联 Cookie 可能不随请求发送。应按框架设计配置关联 Cookie，必要时使用 SameSite=None; Secure，同时保留严格的事务防护。

SameSite 判断的是“同站⁷¹”，CORS⁷² 主要关注“同源”。不同子域可能跨源但同站，不要把这两个概念混用。

本篇名词注释

¹ OA，Office Automation，办公自动化。本文指内部办公系统，常用于请假、报销、审批、公告和日程。

⁵⁶ 发现配置是一份描述身份平台协议地址与能力的配置资料，应用需从可信来源获取。

⁵⁷ JWKS：JSON Web Key Set。用于提供公钥等密钥信息的集合。

⁵⁸ MFA：Multi-Factor Authentication，多因素认证。结合不同类型因素验证身份。

⁵⁹ 中间件：请求处理链中的框架组件。拦截登录请求、处理协议回调。

⁶⁰ SPA，Single-Page Application，单页应用。主要在浏览器中完成页面切换和交互。

⁶¹ CSRF：Cross-Site Request Forgery，跨站请求伪造。防止浏览器被诱导执行带用户身份的请求。

⁶² S256 表示 PKCE 使用 SHA-256 计算摘要的方式。散列将输入转换成固定长度摘要，不是可以解密还原的加密。公式中的 ASCII 是字符编码，Base64URL 是摘要的文本编码。

⁶³ state：登录请求与回调的关联值。关联并验证当前浏览器发起的登录过程。

⁶⁴ nonce：本次认证使用的随机值。检查 ID Token 属于本次认证。

⁶⁵ 302 / 401 / 403：HTTP 状态码。常见含义分别为重定向、缺有效认证、访问被拒绝。

⁶⁶ GET / POST：HTTP 请求方法。通常分别用于获取资源、提交数据。

⁶⁷ issuer / iss：签发者标识。判断结果来自哪个可信平台。

⁶⁸ audience / aud：预期接收者。防止把发给其他应用或 API 的令牌拿来用。

⁶⁹ pairwise subject 是按客户端或客户端分组区分的用户标识。同一人在不同客户端可能有不同 sub，跨应用账号映射需要明确支持。

⁷⁰ subject / sub：主体标识。判断结果对应哪个用户或主体。

⁷¹ 同源依据协议、主机和端口判断；现代浏览器的同站判断主要涉及方案和可注册域等规则。不同子域可能跨源但同站。

⁷² CORS：Cross-Origin Resource Sharing，跨源资源共享。控制网页脚本对跨源响应的读取。

⁹⁰ RFC 是互联网技术规范等文档的编号体系，并非所有 RFC 都是标准；W3C 是制定 Web 技术规范的组织；OWASP 是提供应用安全资料和项目的开放社区。
