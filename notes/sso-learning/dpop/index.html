单点登录与身份认证进阶：发送方约束令牌与 DPoP

发送方约束令牌与 DPoP：从“拿到令牌就能用”到“还要证明持有密钥”

更新日期：2026-11-20
阅读定位：完成单点登录基础学习后的进阶材料。

建议先按单点登录与身份认证学习路线完成第 1～3 篇，尤其是访问令牌、授权码、JWT 与数字签名部分。

本文继续使用同一组参与方：员工小林、第三方日程助手、统一身份平台，以及提供日程 API 的 OA。日程助手有自己的后端，后端取得并保存访问令牌，再调用 OA 查询小林授权开放的日程。

本篇只解决一个问题：如果攻击者复制到了访问令牌，怎样让他不能仅凭这份令牌在其他环境中使用？

悬停名词旁的上标可看释义，点击可跳到文末小字注释。请求、密钥和 JWT 示例用于解释结构，包含占位值，不是可以直接使用的凭据或生产代码。

第一次阅读先看第 1～6 节，理解完整机制。第 7～10 节用于区分相关技术与准备实现，第 11 节用于面试复习。

1. 先回到已经学过的访问令牌

1.1 当前方案已经能完成什么

小林通过浏览器在身份平台完成认证与授权。日程助手后端按授权码流程取得访问令牌，然后调用 OA：

OA 检查令牌是否有效、是否面向 OA API、是否允许读取小林的日程，再返回相应数据。

这种用法常采用 Bearer Token¹。它的关键特征是：令牌持有者通常不需要再证明拥有某把密钥。

1.2 新问题：令牌是真的，但发送请求的人换了

假设令牌从日志或其他不该暴露的位置泄露，攻击者复制它并发送相同形式的请求。

OA 验证令牌签名，发现签名是真的，授权范围和有效期也符合要求。问题在于，令牌中的内容仍然与被复制之前一样。

即使令牌写着“签发给日程助手”，这也只是可信签发方对令牌归属的声明。攻击者复制后，这句话不会自动变成“现在是攻击者在用”。

因此，API 只检查令牌本身，不能据此判断当前请求方是否持有助手独有的秘密。

1.3 方案：令牌与密钥绑定，调用时再提供持有证明

我们增加一个要求：OA 既要看到有效令牌，也要看到请求方能使用令牌绑定的私钥生成合格证明。

这称为发送方约束。它限制的是令牌能够由什么密钥持有者来使用；仅复制令牌不再足够。[R1]

2. 引入具体机制：DPoP

DPoP² 在应用层使用签名证明密钥持有。它可以与 OAuth 授权码流程组合，并不要求先取消授权码或改变小林的授权范围。

先记住两个动作：

  1. 签发令牌时，认证中心在可信的令牌信息中记录绑定的公钥。
  2. 调用 API 时，助手使用对应私钥生成请求证明，API 检查证明与令牌之间的关联。

在本例中，DPoP 密钥由日程助手后端生成并使用，浏览器不用拿到这把私钥。

2.1 这里有两对职责不同的密钥

密钥 由谁掌握 用来做什么
认证中心的签名私钥 认证中心 给访问令牌签名
认证中心的可信公钥 OA API 通过可信配置取得 验证访问令牌的签名
日程助手的 DPoP 私钥 K 日程助手后端 给请求证明签名
与 K 配对的公钥 P 可以传给中心和 API 验证助手生成的请求证明

这些是职责上的区分，不要求每种密钥都单独部署一台服务器。中心的签名密钥与助手的 DPoP 密钥不是同一把。

3. 第一步：签发时怎样把令牌绑定到公钥

3.1 助手生成密钥，并在取令牌时证明持有私钥

日程助手生成一对密钥：私钥 K 保密，公钥 P 可以公开。

后端向身份平台的令牌端点提交授权码等必要数据时，同时附带一份用 K 签名的 DPoP 证明，证明中包含公钥 P。身份平台验证这份证明，并继续执行 OAuth 原本要求的授权码、客户端认证和兑换绑定等检查。

DPoP 证明本身不等于注册应用的身份认证。 任何人都可以生成自己的密钥对；平台不能仅因一个人能用某把私钥签名，就认定他是登记的日程助手。DPoP 与客户端身份验证承担不同职责。

3.2 平台记录公钥 P 的指纹

平台不需要把私钥写入令牌。私钥始终留在助手后端。

在常见 JWT 访问令牌方案中，平台计算公钥指纹³，把指纹写入令牌的绑定声明。Keycloak 的 DPoP 文档展示了这一处理方式。[R2]

公钥通常使用 JWK⁴ 格式表示。指纹必须按规范选取字段、规范化表示，再计算摘要，不能任意对一段格式化后的 JSON 文本做散列。[R3]

3.3 JWT 中的绑定信息长什么样

下面仅展示一部分声明，不是完整令牌：

cnf⁵ 表示密钥确认信息。jkt⁶ 在 DPoP 中表达绑定公钥的 JWK SHA-256 指纹。JWT 的密钥确认声明有专门规范，DPoP 在其中规定了自己的指纹成员。[R4][R5]

认证中心使用自己的签名私钥签发整个访问令牌。因此，公钥指纹 H 和用户、受众等声明一起受到签名保护。

3.4 不透明令牌也可以绑定

发送方约束不要求访问令牌一定是 JWT。如果它是不透明字符串，平台可以在服务端保存令牌与公钥指纹的关联，OA 通过受保护的令牌状态查询取得该关联，再验证请求证明。

差别在于绑定信息从哪里取得：JWT 可以携带已受保护的声明，不透明令牌则通过服务端记录和查询取得。OA 都必须可靠识别它是 DPoP 绑定令牌，不能忽略绑定后按普通 Bearer 令牌放行。[R5]

4.2 请求证明的头部包含公钥

请求证明采用签名 JWT。头部结构可以是：

typ 标明这是 DPoP 证明，不能拿其他用途的 JWT 来替代。alg 是约定的签名算法，示例中的 ES256⁷ 使用椭圆曲线签名。jwk 只包含公钥，OA 可以用它验签。[R2]

4.3 证明还要关联本次调用

只签一句“我是日程助手”不够，因为这句话可能被复制到别的调用里。调用 API 的证明还包含请求和令牌关联信息。以下字段只用于说明结构，示例时间与编号不能复制到真实请求中重复使用：

字段 本例的含义
htm 本次请求的 HTTP 方法
htu 按协议处理的目标 URI，不包含查询部分和片段
iat⁸ 证明的生成时间，单位是秒
jti⁹ 本次证明的唯一编号
ath¹⁰ 当前提交的访问令牌摘要

助手使用私钥 K 给证明签名。OA 检查方法、目标、时间及令牌摘要等条件，避免仅凭一份与当前调用不匹配的证明放行。ath 用来关联证明与访问令牌，不能单独替代时间和重放检查。[R5]

不同请求应生成新的证明。取令牌时的证明与调用 API 时的证明也不同，不能直接重复使用；其中 ath 针对需要提交访问令牌的资源请求。

5. OA API 怎样校验：两层验证，加一次绑定检查

5.1 第一层：验证访问令牌

OA 先按约定验证访问令牌。JWT 方案需要可信签发方、公钥、受众和时间等检查；不透明令牌需要可靠取得其当前状态及元数据。

OA 从通过验证的令牌信息中读取绑定指纹 H。不能从未经验证的任意 JSON 中取一个 H，然后当作可信绑定。

5.2 第二层：验证请求证明与绑定

DPoP 中间件还需要验证证明的类型、允许的算法和签名，并按协议检查请求关联、时效与重放条件。必要时处理服务端要求的 nonce¹¹ 挑战。

两层之间最重要的连接是：

“证明签名有效”还不够，它可能只是攻击者用自己的私钥签的一份证明；“令牌有效”也不够，它可能已被复制。必须把两者对应起来。

5.3 验证成功后，仍要检查业务权限

私钥持有证明不表示可以读取任意员工的日程。OA 仍要检查授权范围、用户状态、租户和资源归属等规则。

6. 攻击者为什么不能换一把自己的密钥

6.1 只有令牌，没有助手的私钥

攻击者能复制令牌，也能看见其中的公钥指纹，但不能仅凭公钥生成助手的有效签名。因此，他无法为自己的新调用生成合格的请求证明。

6.2 攻击者用自己的密钥签证明

攻击者当然可以生成另一对密钥，制作一份签名完全有效的证明。问题在于，这份证明的公钥指纹不等于令牌记录的 H。

6.3 攻击者修改令牌中的指纹

如果攻击者把 cnf.jkt 改成 HQ，认证中心对访问令牌的签名就不能通过验证。攻击者需要中心签名私钥才能伪造这份受保护的绑定，单靠助手的公钥做不到。

因此，绑定不是一段“请相信我使用这把公钥”的自述，而是由认证中心保护的关联。

6.4 令牌和一份请求证明都被复制

此时要依赖时效、请求关联、唯一编号记录和适用的挑战机制降低证明重复使用的风险。不能只检查签名就接受任意旧证明，也不能承诺任何截获情形都绝无抢先使用的可能。

如果攻击者还能使用助手的私钥，或控制助手程序让它代签请求，保护条件就被破坏了。DPoP 不能修复已失守的应用执行环境，私钥和应用安全仍然重要。[R1]

7. 它与授权码、客户端认证、签名和加密的关系

7.1 授权码与 DPoP 保护的阶段不同

机制 在本例中重点处理什么
用户认证与授权 小林是谁，她是否允许日程助手读取日程
授权码与相应兑换保护 将此次授权交接给符合兑换条件的应用，并减少真正令牌经过浏览器的机会
客户端身份验证 兑换方是否能按注册方式证明应用身份
DPoP 请求方是否持有访问令牌所绑定的私钥，并提供适用的请求证明
OA 业务授权 即使上述校验通过，是否仍允许本次数据访问

一个应用可以同时使用授权码、客户端身份验证、PKCE 和 DPoP。DPoP 不是“更高级的授权码”，也不表示只要证明持有某把自建密钥就能读取小林的数据。[R1][R6]

7.2 这里有两种签名，不能混为一谈

API 要同时信任中心签发的授权信息，并检查发送方满足密钥绑定要求。中心的签名不会自动替助手生成每次请求的持有证明。

7.3 加密内容不等于防止复制使用

如果 API 直接接受加密后的令牌，攻击者可能原样提交那段密文，而不必理解其中内容。内容保密与限制使用者是不同要求。

如果把真正令牌加密给指定后端，只允许后端解密取出令牌，则可以保护交付，但它需要相应的密钥管理和协议设计。不能仅凭“用了加密”就判断是否已防止令牌滥用。

DPoP 主要增加密钥持有约束，不负责把访问令牌内容加密。仍然需要 HTTPS 保护传输。[R1][R7]

8. DPoP 的边界与工程上的状态

8.1 请求证明不等于给整个 HTTP 请求签名

标准证明关联方法和目标 URI，并在 API 访问时关联令牌摘要，但不覆盖整个请求体和所有请求头。htu 也不包含查询部分和片段。

因此，不应声称“DPoP 让整个请求都无法被修改”。传输完整性仍依赖 HTTPS；如果业务还需要额外的消息完整性保护，应单独设计，而不是默认 DPoP 已覆盖所有内容。[R5]

8.2 防重放需要状态和时间策略

接收方要按规则处理证明的时间窗口、唯一编号和适用的 nonce。只把 jti 放入证明而完全不检查重复，不会自动产生防重放效果。

用于检测重复的记录可以放在短期缓存中，保存与已接受证明及其密钥、上下文相关的标识，保留时长依据协议接受窗口和挑战策略确定。不要无限保存完整请求证明。

多个 API 实例必须确保这些检查在部署范围内有效，不能让相同证明换个实例就绕过需要的重复检查。具体存储和一致性方式属于实现选择。

DPoP 的 nonce 不应机械理解成“每个请求都向中心再要一个值”。是否要求挑战、由哪个服务要求、何时更新，应按协议与平台实现处理。

8.3 私钥和令牌要作为一组管理

数据 本例中适合的保存位置或管理方式
DPoP 私钥 助手后端受保护的密钥存储或签名设施
公钥及其指纹 可以保存或传递，不属于保密凭据
访问令牌 助手后端受保护的令牌存储，并记录对应密钥
请求证明 每次生成并发送，通常不作为长期业务数据保存
已接受证明的识别信息 API 按防重放策略短期保存

如果多个助手实例都要使用同一个绑定令牌，它们需要能安全地使用对应的签名能力，或者采用按实例管理令牌与密钥的方案。不能让一个实例拿到令牌，却没有对应密钥。

轮换密钥时，已经绑定旧公钥的令牌不会自动改绑新公钥。要协调旧令牌过期、重新取令牌和旧密钥保留；若刷新令牌也受密钥绑定约束，还要纳入同一生命周期设计。

9. 另一条实现路径：mTLS 证书绑定

mTLS¹² 可以在 TLS 连接阶段要求客户端使用证书证明身份。授权服务器把访问令牌与客户端证书绑定，资源 API 检查当前连接使用的证书是否与令牌绑定一致。

它与 DPoP 的共同目标是：令牌之外还需要发送方的密钥证明。区别在于，证明主要发生在什么层：

方案 证明主要发生在哪里 常见工程关注点
DPoP 应用层请求证明 签名、请求关联、证明校验与重放控制
mTLS TLS 连接与客户端证书 证书发放、连接终止位置、可信证书信息的传递

只是启用了双向 TLS，并不代表所有令牌都已经完成绑定。令牌签发方与 API 还需要执行证书绑定和匹配规则。对于 JWT，可用 cnf 下的 x5t#S256 表达证书指纹。[R8]

当前学习阶段先掌握“可信令牌中的密钥关联 + 请求方的密钥持有证明”，再分别学习 DPoP 和 mTLS 的部署细节即可。

10. 怎样接入和验证，而不是自行拼算法

10.1 实现职责

先确认身份平台、客户端库和资源 API 中间件支持相同的 DPoP 能力，再选择集成方式。

  • 身份平台检查取令牌请求中的证明，签发绑定令牌。
  • 客户端库管理密钥和对应令牌，为每次调用生成适用的新证明。
  • API 中间件识别绑定令牌，完成令牌、证明、绑定和重放等校验。
  • 业务代码在验证成功的身份与授权上下文中，执行日程访问规则。

应使用经过维护的协议库和平台能力，不要把本文的字段说明拼成一套自制验证器。接口代理、URL 规范化和多实例状态都会影响实际校验。

10.2 建议的学习实验

以下是验证思路，本文没有实际搭建或运行这些系统。

重复提交证明 按测试环境设置重复相同证明 相应的防重放策略应生效
使用错误权限 协议证明都正确，但访问未授权日程 业务授权仍应拒绝

测试只在自己授权的环境进行。不要把真实令牌、私钥和完整证明复制到公开调试网站，日志也应避免记录这些数据。

11. 面试复习

11.1 一分钟讲解

Bearer Token 的问题是，令牌被复制后，攻击者可能直接使用。发送方约束令牌在有效令牌之外，还要求调用方证明持有绑定密钥。

以 DPoP 为例，助手生成一对密钥，平台在签发令牌时记录公钥指纹。助手每次调用 API 都用私钥生成新的请求证明，关联请求方法、目标和访问令牌。API 同时验证令牌、证明、密钥绑定和适用的时效与重放条件，最后检查业务权限。

只有被盗令牌，没有对应私钥，攻击者就无法为自己的新调用生成合格证明。DPoP 不代替用户授权、客户端认证或 HTTPS，也不能解决客户端已被控制的问题。

11.2 高频追问

问题 回答要点
令牌怎样绑定到密钥 由签发方保护令牌与公钥指纹的关联，API 必须执行匹配检查
为什么不能换成攻击者自己的公钥 证明的公钥指纹必须匹配令牌中经过验证的绑定
修改令牌中的绑定不就可以了吗 会破坏中心签发令牌的完整性保护
公钥也公开，为什么攻击者不能签名 公钥用于验签，生成签名需要对应私钥
为什么需要两层签名 中心签令牌，助手签请求证明，分别表达授权与密钥持有
与授权码是不是重复 授权码处理授权交接和令牌取得，DPoP 约束令牌使用，职责不同
DPoP 就证明了注册应用身份吗 不必然。自建密钥持有证明与注册应用的客户端认证不同
能替代 HTTPS 吗 不能，证明不覆盖所有请求内容，也不提供传输保密
有 jti 就能防重放吗 不能，还要按协议结合状态记录、时间及适用挑战检查
私钥被盗后呢 攻击者可能生成证明，需要保护密钥、撤销相关授权并处理受影响凭据

13. 名词注释

¹ Bearer Token，持有者令牌。使用方通常持有有效令牌即可访问相应资源，无需额外证明持有某把密钥。

² DPoP，Demonstrating Proof of Possession，通过应用层的签名证明密钥持有，并约束访问令牌的发送方。

³ 公钥指纹，thumbprint。按指定规范对公钥表示计算出的摘要，用于稳定标识这把公钥。

⁴ JWK，JSON Web Key，以 JSON 对象表示密钥。本文在证明头部传递公钥 JWK，不能包含私钥。

⁵ cnf，confirmation，令牌中表达密钥确认信息的声明。DPoP 使用其 jkt 成员表示公钥指纹。

⁶ jkt，JWK thumbprint，DPoP 令牌绑定使用的 JWK SHA-256 指纹成员。

⁷ ES256，一种基于椭圆曲线的数字签名算法标识。示例采用这个名字，不表示所有部署必须使用它。

⁸ iat，issued at，签发或生成时间。这里表示请求证明的生成时间，使用 Unix 时间戳秒数。

⁹ jti，JWT ID，JWT 的唯一标识。这里为每次请求证明生成新值，服务端配合记录检测重复使用。

¹⁰ ath，access token hash，访问令牌值的 SHA-256 摘要经 Base64URL 编码后的值，用来绑定证明与当前令牌。

¹¹ nonce，服务端给出的挑战值。DPoP 中适用时由客户端放进后续证明；它不同于基础文档中 OIDC ID Token 的 nonce。

¹² mTLS，mutual TLS，双向 TLS。客户端与服务端按配置使用证书进行认证，可用于证书绑定访问令牌。
