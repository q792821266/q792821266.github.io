单点登录与身份认证

单点登录与身份认证：学习与面试指南

更新日期：2026-11-19
适用对象：后端、全栈、平台开发，以及需要理解企业统一登录的工程师。

本文用同一个例子展开：公司有 OA、CRM 和统一认证中心。用户登录 OA 后，再打开 CRM，希望无需重复输入密码。示例域名均为教学用途，代码为框架无关伪代码，不是可直接部署的认证服务。

  • 准备面试：复习第 13～15 节，再用第 16 节的小实验验证理解。

1. 先分清基本概念

1.1 身份标识、认证、授权与审计

概念 解决的问题 例子
身份标识 Identification 你声称自己是谁 输入员工号，选择公司租户
身份认证 Authentication，AuthN 如何验证这个身份 密码校验、通行密钥签名、MFA
授权 Authorization，AuthZ 这个身份可以做什么 可查看客户，但不可导出全部客户
审计 Auditing 谁在何时做了什么 记录员工修改客户资料的操作
会话 Session 后续请求如何延续登录状态 浏览器携带会话 Cookie
单点登录 SSO 多个应用如何复用一次认证 登录 OA 后访问 CRM 无需再次输密码
身份联合 Federation 不同系统或组织如何信任身份结果 SaaS 信任客户公司的身份平台

SSO 是一种使用体验和系统能力，可以由不同协议实现。SAML、OIDC、CAS 都能参与实现 SSO。

身份联合强调信任关系，SSO 强调减少重复认证。联合登录后，应用仍可能要求补充验证或接受条款，因此二者并非完全等同。

1.2 登录成功，不代表可以访问所有资源

员工通过公司认证后，CRM 还要判断：

  • 账号是否启用，是否属于当前租户。
  • 是否拥有 CRM 使用资格。
  • 是否有查看客户的权限。
  • 目标客户是否属于该员工可访问的数据范围。

因此，一次完整请求通常包含：识别会话或令牌 → 验证身份状态 → 检查操作权限 → 检查资源归属 → 执行业务并审计。

常见权限模型包括 RBAC 和 ABAC。RBAC 按角色分配权限；ABAC 根据用户、资源、动作和环境属性决策。实际系统常组合使用，例如先检查“销售经理”角色，再限制到本租户、本区域的数据。

1.3 认证系统真正需要保护什么

攻击者不一定需要破解密码。拿到有效的会话 ID、Bearer Token，或者让应用接受伪造的认证结果，同样可能冒充用户。

因此要保护整个链路：凭据验证、认证结果传递、会话保存、接口授权、退出与恢复流程。只把密码加密传输远远不够。

2. 身份认证的思想与常见方式

2.1 认证依赖可验证的证明

系统无法直接知道屏幕前的人是谁，只能验证某种证明，并据此建立信任。

因素 常见证明 主要问题
知识因素，你知道什么 密码、PIN 猜测、撞库、钓鱼
持有因素，你拥有什么 安全密钥、手机中的密钥、OTP 设备 设备丢失、验证码转交、恢复机制被绕过
生物因素，你是什么 指纹、人脸 依赖设备与传感器安全，不能像密码一样方便更换

MFA 是多因素认证。密码加另一个密码仍属于同一类因素；密码加基于设备的 OTP 通常涉及两类因素。

短信验证码只能证明对手机号接收通道的控制，可能受到 SIM 换卡、转发和钓鱼影响，不能简单视为高强度认证。

2.2 密码登录的实现要点

典型过程：

  1. 浏览器通过 HTTPS 提交账号和密码。
  2. 服务端查找用户，执行限速与风险判断。
  3. 使用密码散列算法验证密码。
  4. 必要时要求第二因素。
  5. 创建新的登录会话，记录认证方式和时间。

密码应使用 Argon2id、scrypt、bcrypt 等适合密码的算法保存，并为每个密码使用独立随机盐。具体算法与参数要结合平台能力、合规约束和服务器成本配置。普通 SHA-256、MD5 太快，不适合作为单独的密码存储方案。

盐可以和散列一起保存，用来避免相同密码产生相同结果，并增加预计算攻击成本。可选的 pepper 是额外的服务端秘密，应与数据库分开保管。

还要考虑撞库限速、泄露密码检查、避免账号枚举，以及找回密码流程。无限期锁定账号可能被攻击者用来拒绝正常用户登录，应结合限速、风险验证和恢复机制设计。

2.3 通行密钥与 WebAuthn

通行密钥通常使用 WebAuthn/FIDO 体系中的公钥凭据。注册时生成密钥，服务端保存公钥；登录时服务端发出随机挑战，认证器使用私钥签名，服务端验证签名、挑战和站点绑定信息。

私钥通常由设备或凭据提供方管理。用户用指纹、面容或 PIN 解锁凭据，并不意味着网站会收到指纹或人脸数据。部分通行密钥可以通过凭据提供方同步，不能笼统认为私钥永远只存在一台设备上。

站点绑定能抵御许多常见的凭据钓鱼攻击，但应用中的恶意脚本、会话盗用和不安全的账号恢复仍然需要防护。[R8]

2.4 认证强度与重新认证

查看普通页面和修改收款账户可以要求不同强度。系统可以复用现有会话，但在敏感操作前要求近期认证或更强因素，这通常称为 step-up authentication。

在 OIDC 中可以结合 auth_time、max_age、acr、amr 与身份平台策略实现。仅发送一个“要求 MFA”的参数，并不保证平台已经执行；必须检查实际返回结果以及双方约定的语义。

3. 从单应用登录到单点登录

3.1 单应用登录

sequenceDiagram
    participant B as 浏览器
    participant A as 应用服务
    participant D as 用户库与会话库
    B->>A: 提交凭据
    A->>D: 验证用户并创建会话
    A-->>B: Set-Cookie: session=随机值
    B->>A: 后续请求携带 Cookie
    A->>D: 查会话并检查状态
    A-->>B: 返回有权访问的资源

HTTP 请求之间不会自动记住“这个用户刚刚登录过”。应用通过 Cookie、会话或令牌建立这种关联。

3.2 多应用各自登录的问题

如果 OA、CRM、报销系统各自管理密码，会出现重复登录、密码策略不一致、离职停用遗漏，以及重复建设 MFA 和风控的问题。

统一用户库可以减少重复账号，但并不自动实现 SSO。如果各系统仍各自要求输入密码，它们只是共享了账号来源。

3.3 SSO 的核心思想

把身份认证交给受信任的认证中心，各业务应用验证认证结果，再建立自己的登录状态。

graph LR
    U["用户与浏览器"] --> OA["OA：本地会话与业务权限"]
    U --> CRM["CRM：本地会话与业务权限"]
    OA -->|OIDC 或 SAML| IDP["统一认证中心：认证与中心会话"]
    IDP -->|认证结果| OA
    CRM -->|OIDC 或 SAML| IDP
    IDP -->|认证结果| CRM
    IDP --> DIR["用户目录与 MFA"]

OA 不需要保存公司账号的密码，也不应该让用户把认证中心的密码交给 OA 代为登录。

3.4 SSO 通常有多份独立会话

假设三个站点分别是：

状态 通常由谁管理 用途
中心会话 认证中心 判断用户是否已经完成认证
OA 本地会话 OA 让浏览器持续使用 OA
CRM 本地会话 CRM 让浏览器持续使用 CRM
API 令牌及授权记录 授权服务器与资源服务 控制对 API 的访问

这些状态有不同的有效期。OA 会话过期后，可能通过认证中心的现有会话重新建立，无需用户输入密码。认证中心会话过期，也不意味着 OA 的本地会话立即消失。

3.5 跨域 SSO 为什么可行

浏览器不能把 OA 的 Cookie 任意发送给 CRM。跨域 SSO 通常依靠浏览器跳转，让浏览器实际访问认证中心，再把可验证的协议结果传回业务应用。

用户访问 CRM 时，CRM 跳转到认证中心；浏览器在访问认证中心时携带认证中心自己的 Cookie。认证中心识别已有登录，向 CRM 返回新的认证结果，CRM 再创建自己的 Cookie。

这解释了“第二次登录没有输密码，但仍发生几次跳转”的现象。

同一父域下设置 Domain=example.com 可以让部分子域共享 Cookie，但会扩大信任范围，受控程度较弱的子域可能影响其他应用。跨不同可注册域不能这样共享。共享 Cookie 只是某些部署方案，不能作为 SSO 的通用定义。

4. Cookie、Session、Token 与 JWT

4.1 它们处在不同层次

名称 是什么 是否天然安全
Cookie 浏览器保存并按规则附带数据的机制 需要正确设置属性并防范 CSRF、泄露
Session 服务端识别一段持续交互的状态或机制 需要随机标识、过期、撤销等控制
Token 用于表达某种凭证或权限的数据 要看类型、验证规则和使用场景
JWT 一种声明编码格式 解码、签名验证、授权是不同步骤

Cookie 可以装随机 Session ID，也可以装 Token。Session 可以存 Redis、数据库或其他受保护的存储。因此，“Cookie 和 Session 选哪个”通常不是准确的问题。

4.2 不透明令牌与自包含令牌

不透明令牌对接收方表现为随机字符串，接收方需要查询本地记录或调用受保护的 introspection 接口确认状态。[R7]

自包含令牌携带声明，例如签名 JWT，资源服务可以在本地验签并检查声明。这样减少了逐次远程查询，但用户禁用、授权变更、令牌撤销等状态仍可能需要额外查询或事件同步。

4.3 JWT 要理解的边界

常见的签名 JWT，使用 JWS 紧凑形式时长这样：

签名用于检验内容完整性和签发来源，不提供内容保密性。任何拿到这类 JWT 的人通常都能解码 payload，因此不应放入密码、私钥等秘密。JWT 也可以采用 JWE 加密形式，但不能假设所有 JWT 都已加密。

常见声明包括：

声明 意义 常见错误
iss 签发者 接受其他环境或其他租户签发的令牌
sub 主体标识 误用邮箱代替稳定的主体 ID
aud 预期接收者 API 接受发给另一个 API 的令牌
exp 到期时间 只验签，不验时间
nbf 不早于此时生效 忽略尚未生效的令牌
iat 签发时间 误认为它本身决定有效期
jti 令牌标识 误认为有这个字段就自动防重放

字段是否必需取决于令牌类型和协议约定。jti 只有配合服务端记录或专门机制才可能用于重放检测。

HS256 使用共享秘密签名和验签，持有该秘密的验证方也具备签发能力。RS256、ES256 等非对称算法能让业务服务仅持公钥验签，但仍需正确管理私钥与信任关系。

4.4 Session 与 JWT 如何选择

关注点 服务端会话或不透明令牌 本地校验的短期 JWT
主动失效 删除或修改服务端状态较直接 通常要等到期，或增加撤销机制
每次校验成本 通常要查询状态，可缓存 通常本地验签和检查声明
分布式扩展 需要可靠的会话或令牌状态服务 需要可靠的公钥分发和轮换
权限更新 查询最新状态更直接 嵌入的权限可能过时
系统状态 显式保存会话 仍有用户、刷新令牌、密钥等状态

浏览器业务系统常采用本地 Session；面向多资源服务的 API 常采用 Access Token。两者也可以组合：浏览器拿 Session Cookie，应用后端拿 Access Token 调 API。

5. 常见协议与技术选型

5.1 对照表

技术 核心用途 典型场景 需要记住的区别
OIDC 标准化用户认证和身份声明 现代 Web、App、企业登录 在 OAuth 2.0 上增加身份层
OAuth 2.0 委托授权 第三方应用访问网盘、日历等 API 核心关注访问授权
SAML 2.0 传递认证与属性等声明 企业 SaaS、传统企业 SSO 常见 Web SSO 使用 XML 与签名
CAS 集中认证和单点登录 高校、已有 CAS 的企业系统 围绕票据与服务端验证工作
Kerberos 基于票据的网络认证 Windows 域、企业内网服务 常依赖域、KDC、时间同步
LDAP 目录访问 查询用户、部门、组与凭据校验 目录协议本身不等于 Web SSO
WebAuthn/FIDO2 公钥凭据认证 通行密钥、安全密钥、MFA 可用作认证中心的认证方式
SCIM 用户与组的配置和生命周期管理 企业向 SaaS 同步账号、停用账号 处理账号管理，不完成浏览器登录

LDAP 是协议；Active Directory 是目录服务产品体系，通常涉及 LDAP、Kerberos 等多种协议。不要把二者直接画等号。

5.2 OAuth 2.0 与 OIDC

OAuth 2.0 的典型问题是：“用户是否允许这个图片应用读取网盘里的照片？”授权服务器签发 Access Token，图片应用拿它访问网盘 API。

OIDC 进一步规定应用如何获得和验证用户身份，使用 openid scope 和 ID Token，并可通过 UserInfo 获取约定的用户声明。[R1]

有些平台提供基于 OAuth 的“登录”，再调用平台自定义用户接口识别用户。这是具体平台定义的组合，不能据此认为拿到任意 OAuth Access Token 就能安全完成标准身份认证。

5.3 三种令牌不能混用

类型 主要接收方 用途
ID Token OIDC 客户端，即业务应用 让客户端确认这次认证结果
Access Token 资源服务器，即 API 访问被授权的资源
Refresh Token 授权服务器的 Token Endpoint 获取新的 Access Token，受服务端策略限制

ID Token 通常是 JWT；Access Token 可以是 JWT，也可以是不透明字符串。Refresh Token 不是每次登录都会返回，是否签发取决于授权、scope 和平台策略。

不能因为 ID Token 验签成功，就把它当作调用任意 API 的凭据。API 应验证面向自己的 Access Token，并执行授权。

5.4 如何选择

  • 新建 Web、移动端认证体系，通常优先评估 OIDC。
  • 接企业客户 SSO，优先尊重客户身份平台支持的协议，SAML 2.0 和 OIDC 都很常见。
  • 已有 CAS 的学校或企业，可直接接 CAS，避免为协议偏好增加迁移成本。
  • 企业内网域环境可使用 Kerberos；需要接现代应用时，可以通过身份平台桥接到 OIDC 或 SAML。
  • 只有一个业务应用时，成熟框架的本地认证与 Session 可能已经足够，SSO 需要由实际的多应用需求驱动。

认证中心也可以同时支持多种协议。业务系统用 OIDC 接认证中心，认证中心再通过 SAML 联合客户身份平台，是常见的身份代理架构。

6. OIDC 授权码加 PKCE 的完整流程

本节以“有应用后端的 Web 系统”为例。后端保管令牌，浏览器持有本地 Session Cookie。

6.1 角色和信任配置

角色 示例 责任
用户与 User Agent 用户和浏览器 发起访问，完成交互认证
Client / RP OA 后端 发起登录，验证结果，建立本地会话
OP / Authorization Server 统一认证中心 认证用户、管理授权、签发令牌
Resource Server 客户 API 验证 Access Token，检查业务权限

身份平台中先注册 OA，设置 client_id、精确回调 URI、允许流程，以及适用的客户端认证方式。配置可信 issuer，通过受信任的发现配置获取授权、Token 和 JWKS 端点。

公开客户端无法可靠保守秘密，例如纯 SPA 和安装到用户设备上的原生 App。机密客户端具备受保护的后端，可以用客户端密钥或其他方式认证。把 client_secret 放进前端构建产物，并不会让 SPA 成为机密客户端。

6.2 时序图

sequenceDiagram
    participant B as 浏览器
    participant A as OA 后端
    participant I as 认证中心
    participant R as 业务 API
    B->>A: 访问受保护页面
    A->>A: 创建 state、nonce、PKCE 登录事务
    A-->>B: 302 跳转授权端点
    B->>I: 授权请求与认证中心 Cookie
    I->>I: 使用已有中心会话或要求用户认证
    I-->>B: 302 回调，携带 code 和 state
    B->>A: GET /auth/callback?code=...&state=...
    A->>A: 检查并消费登录事务
    A->>I: 后端用 code 和 code_verifier 换令牌
    I-->>A: ID Token、Access Token 等
    A->>A: 验证认证结果并创建本地会话
    A-->>B: Set-Cookie 后跳转干净业务地址
    B->>A: 使用本地会话访问功能
    A->>R: 携带 Access Token 调 API
    R-->>A: 校验令牌并检查权限后的结果
    A-->>B: 页面或业务数据

这个流程中的“前通道”经浏览器传递，例如授权跳转和回调；“后通道”由服务端直接通信，例如后端换取令牌。

6.3 授权请求

以上换行仅用于阅读，实际请求要正确编码。API scope 应按业务最小需要额外申请；openid profile email 不代表自动拥有任意业务 API 权限。

机制 与什么关联 主要保护目标 应用侧检查
state 请求与回调，以及发起请求的浏览器事务 防止不匹配的回调、登录 CSRF，并关联受保护的跳转上下文 随机、短期、一次性，绑定浏览器，匹配并消费

6.5 兑换与验证

客户端还需按注册方式提供 client_id 和客户端认证。不要把生产密钥写入示例 URL、日志或前端代码。

应用应通过成熟 OIDC 库验证 ID Token，显式配置可信 issuer、自己的 client ID、允许算法与必要的时间容差。要检查签名、iss、aud、有效期和本次 nonce，并按适用规则检查 azp、多 audience 等情形。只做 Base64 解码不能完成验证。

如果调用 UserInfo，须检查其 sub 与已验证 ID Token 中的 sub 一致，避免把另一个人的资料绑定到当前登录。

建立外部身份映射时使用稳定的 (issuer, subject)。不同客户端可能获得 pairwise subject，跨应用账号关联必须有身份平台支持或明确的可信映射，不能假设所有客户端的 sub 永远相同。

6.6 为什么先拿 code，再换 Token

授权码是短期、一次性、绑定客户端与重定向上下文的中间凭证。后端可以通过受保护的后通道换取令牌，避免把可长期使用的令牌直接放在浏览器地址栏。

URL 中的 code 仍需保护。它可能进入浏览历史、代理日志或错误采集系统。回调页应尽快处理并跳转到干净地址，避免加载会泄露参数的第三方资源。

新系统通常采用授权码加 PKCE。不要照搬旧教程的隐式流程直接返回 Access Token；资源所有者密码凭据模式要求应用收集用户密码，也不适合作为新的接入方案。[R2]

7. SAML 与 CAS 的具体流程

7.1 SAML 2.0 Web SSO

SAML 的身份提供方叫 IdP，业务应用叫 SP。常见接入需要交换 metadata，约定 Entity ID、SSO 地址、ACS 地址、签名证书，以及用户标识和属性映射。

下面描述常见的 SP 发起流程，使用 Redirect 发送认证请求、POST 返回响应：

  1. 用户访问 OA，OA 没有有效本地会话。
  2. OA 创建 AuthnRequest，并通过浏览器发送给 IdP。
  3. IdP 检查中心会话，必要时要求认证。
  4. IdP 生成包含认证声明的 SAML Response。
  5. 浏览器通过表单把 Response POST 到 OA 的 ACS。
  6. OA 验证可信签名及协议约束，提取身份，创建本地会话。

实际签名可能覆盖 Response、Assertion 或双方约定的结构；必须确认应用使用的身份声明确实在有效签名保护范围内。完整验证还应覆盖受众、接收地址、时间限制、请求关联与一次性使用等规则。

签名证明来源与完整性，加密保护内容机密性。两者解决不同问题。不要只检查 XML 里“存在 Signature 标签”，也不要自行拼接 XML 签名校验逻辑，应使用维护良好的 SAML 实现。[R4]

IdP 发起登录没有 SP 预先创建的请求上下文，不能套用相同的请求关联检查；是否支持以及如何限制，需要单独配置风险策略。

7.2 CAS

CAS 使用中心登录状态和 Service Ticket，常缩写为 ST。

  1. 浏览器访问 OA，OA 重定向到 CAS，并传入已登记的 service 地址。
  2. 用户完成 CAS 认证，或复用现有 CAS 中心会话。
  3. CAS 通过浏览器把 ST 带回 OA。
  4. OA 后端携带 ST 和自己的 service 地址向 CAS 验票。
  5. CAS 验证票据与目标服务的绑定，返回认证结果。
  6. OA 创建自己的本地会话。

ST 是面向特定服务的票据，校验尝试会消耗它，不能把它当作长期 Access Token。验票时的 service 地址不匹配，是 CAS 接入的常见失败原因。[R6]

7.3 三种流程的共同思想

业务应用先把用户送到认证中心，再验证返回结果，最后建立自己的状态。差异主要在凭证格式、传递方式、验证规则和生态能力。

不要把它们的所有字段强行一一对应。例如 SAML Assertion 不是 OAuth Access Token，CAS ST 也不是 OIDC ID Token。

8. 如何实现一个可维护的登录系统

8.1 推荐起点

把协议签发和验证交给成熟身份平台与框架中间件。业务团队主要实现账号映射、会话策略、权限校验、审计和生命周期集成。

可以选择 Keycloak 等自建身份平台，或企业已采用的托管身份服务。协议、MFA、联合登录、运维能力和团队成本应一起考虑。自行从零实现 IdP 通常比接入一个 IdP 复杂得多。

9. 退出、续期、撤销与账号生命周期

9.1 先明确需要结束哪种状态

操作 直接影响 通常不会自动完成
本地退出 当前应用 Session 认证中心退出、其他应用退出
中心退出 IdP/OP 中心会话 已有业务会话全部立即失效
全局退出 SLO 按协议通知多个应用结束会话 所有 API 令牌立即失效
撤销刷新令牌 阻止继续使用该令牌续期 现有自包含 Access Token 立即失效
停用账号 后续认证或授权受限 已下发会话、API Key 和令牌全部瞬时失效

只清除浏览器 Cookie 并不保证服务端会话已失效。退出时应让服务端会话失效，并清理对应 Cookie。

9.2 为什么“退出 OA 后又自动登录了”

OA 清除了本地会话，但认证中心会话仍有效。用户再次访问 OA 时，又通过认证中心无交互登录回来。

这是会话范围不同造成的现象。产品要明确“退出此应用”和“退出公司统一账号”分别意味着什么，并使用身份平台支持的退出能力。

9.3 全局退出如何实现

OIDC 可结合 RP 发起退出、前通道退出和后通道退出等规范，具体取决于平台支持。SAML 和 CAS 也有各自的退出机制。

后通道退出由认证中心直接请求应用，应用校验 Logout Token，再根据受信任的 iss 与 sid 或 sub 定位本地会话并失效。验证需要覆盖签名、受众、时间、事件类型和重放控制；Logout Token 不能当成 ID Token 使用。[R5]

应用需要维护中心会话与本地会话的映射。处理应幂等，重复收到退出通知也能安全成功；通知失败要有重试、可观测性和最终过期兜底。

前通道依赖浏览器，可能受到第三方 Cookie 限制、页面关闭或网络失败影响。后通道减少了对浏览器的依赖，但仍存在消息丢失、服务不可达和部分成功的问题。

9.4 Access Token 与 Refresh Token

Access Token 宜按风险设置较短寿命；Refresh Token 用于在策略允许时续期。示例可以是分钟级 Access Token 和更长但有绝对期限的刷新会话，具体数值应由风险、用户体验和身份平台能力决定。

刷新令牌轮换通常意味着每次成功刷新都会签发新刷新令牌，旧令牌失效。检测到旧令牌被再次使用时，平台可撤销相关令牌族，限制被盗令牌的持续使用。

浏览器或后端若并发刷新同一个令牌，正常请求也可能触发复用检测。可按会话串行刷新，使用 single-flight 或有边界的锁与版本控制，并原子更新令牌记录。不要在超时后无条件用旧 Refresh Token 重试。

9.5 “必须立即下线”怎么实现

先明确“立即”的范围和允许延迟，例如 10 秒内禁止新的敏感 API 请求，而非只说“实时”。

可组合采用：

  • 服务端会话失效与跨节点同步。
  • 令牌 introspection 或关键请求查询账号状态。
  • JWT 撤销列表、用户会话版本或权限版本检查。
  • 退出与停用事件通知，加短期缓存。
  • 短寿命 Access Token，降低离线校验的最长暴露时间。

本地验签的 JWT 如果不查询任何最新状态，通常只能等它到期。这是减少远程依赖与及时失效之间的取舍。

9.6 SSO 不负责全部账号生命周期

入职需要创建账号和成员关系，调岗需要调整权限，离职需要停用账号、撤销会话和凭据。

JIT provisioning 在首次联合登录时创建本地账号，适合减少开通步骤，但无法单独保证离职及时停用。SCIM 提供用户、组等资源的标准管理接口，可以用于开通、更新和停用同步。[R9]

停用后还要检查长期 API Key、服务账号、离线任务和本地备用账号，它们可能独立于浏览器 SSO。

10.1 网关统一认证是否足够

网关可以集中校验会话或令牌，并把身份上下文传给内部服务。但业务服务仍要检查资源级权限和租户边界。

如果使用 X-User-Id 等身份头，网关必须移除外部同名头，再写入自己的可信上下文。内部服务要限制访问来源，使用经过认证的链路或可验证上下文，否则攻击者可能绕过网关伪造身份头。

10.2 同站与同源不同

https://oa.example.com 和 https://api.example.com 通常是跨源、同站。它们可能受 CORS 限制，但 SameSite 的行为不能按“跨源”直接推导。

同源关注协议、主机和端口；现代浏览器的同站判断关注方案和可注册域等规则。Cookie、CORS 和 SSO 协议各自解决不同问题。

10.3 多租户 SaaS 的账号定位

通过租户入口或受保护的组织选择确定可信的身份平台配置。邮箱后缀可以帮助路由，但不能单独证明用户属于某个企业租户。

动态接入客户 metadata 或 discovery URL 时，要校验配置来源、限制可访问地址和重定向，避免 SSRF，也避免接受攻击者的签发者。应用应把登录事务绑定到预期租户和 issuer，不能在回调时随意切换。

11.2 为什么不建议长期把敏感令牌放 localStorage

localStorage 可被同源 JavaScript 读取，发生 XSS 时令牌可能被直接窃走，攻击者可以在其他设备使用。

BFF 配合 HttpOnly Cookie 可以减少令牌直接暴露给脚本的机会，但恶意脚本仍可能借当前会话操作业务。采用 Cookie 后，还应处理 CSRF。安全设计需要同时考虑令牌窃取与带身份的恶意请求。

纯 SPA 的可选方案与约束不同，应按身份平台和浏览器应用最佳实践设计。内存保存令牌能减少持久化泄露，但刷新页面、静默续期和恶意脚本执行仍需处理。

11.3 Bearer Token 为什么容易被重放

Bearer 表示持有者通常无需额外证明就能使用。有效签名只证明令牌的签发来源，不证明当前发送者就是最初得到它的客户端。

高风险 API 可以评估 DPoP 或 mTLS 等令牌发送方约束机制。它们增加部署与验证成本，也不能替代权限检查。

11.4 密钥与证书轮换

认证中心可能使用新私钥签名，并通过 JWKS 发布对应公钥。资源服务应缓存可信公钥，对未知 kid 进行受控刷新，避免每个未知值都触发无界网络请求。

新旧公钥需要适当重叠，覆盖仍有效的旧令牌。不能一发布新密钥就立刻移除所有旧公钥，也不能无限信任缓存中的旧密钥。

SAML 签名证书与网站 HTTPS 证书是不同配置，更新网站证书并不自动更新 SAML 信任。应对证书更换、metadata 更新和平台差异做联调。

11.5 账号绑定为什么危险

同一个邮箱可能被回收、修改，或在不同提供方有不同可信度。即使返回 email_verified=true，也仍需评估提供方是否被允许为该组织确认邮箱以及本地账号绑定策略。

绑定一个新身份通常应要求用户已登录原账号并再次验证，或者经过受控的企业管理员流程。账号合并属于身份安全操作，不能仅当作资料去重。

12.2 按链路定位

  1. 确认用户、浏览器、应用、租户和环境，避免把测试环境与生产混用。
  2. 检查浏览器 Network 中的跳转链，记录关键请求与状态码。
  3. 检查 Cookie 是否设置，以及后续请求是否实际发送。
  4. 检查登录事务是否存在、是否绑定当前浏览器、是否已经消费。
  5. 检查后端换码请求和协议库验证错误。
  6. 检查本地会话创建，以及应用和 API 各自的授权判断。
  7. 最后检查退出、权限同步、缓存与多节点一致性。

不要把 Token、Cookie、密码或完整 SAML Response 粘贴到公开解码网站。调试可在受控环境本地解码；日志记录错误码、关联 ID、issuer、client ID 等必要信息，用户标识和网络信息按隐私要求处理。

12.3 可用性与故障范围

认证中心不可用时，新登录、续期和依赖实时校验的请求会受影响。已经建立的本地会话、能够离线验证且仍有效的 JWT，可能继续工作，取决于业务的实时状态检查策略。

设计上应考虑认证中心多实例、会话库可用性、密钥保护、发现配置与 JWKS 的合理缓存、限速、超时和容量规划。某个业务应用被攻破后的影响范围，也取决于它是否能拿到中心凭据或过大权限。

不要为了“降级”而接受未验证的令牌，或自动开放管理员登录。备用访问方式需要事先设计、限制范围并审计。

13. 系统设计面试回答框架

题目示例：“给企业设计一个支持多个业务系统的单点登录平台。”

13.1 先明确需求

询问或主动说明假设：

  • 面向员工还是外部客户，多少应用和用户，是否多租户。
  • 是否已有 AD、LDAP、企业身份平台，必须支持哪些协议。
  • Web、App、CLI 是否都需要支持。
  • 是否需要 MFA、敏感操作重认证、全局退出、立即下线。
  • 可用性、登录峰值、恢复时间、审计和权限更新延迟要求。

13.2 给出结构与一次完整流程

说明认证中心、业务应用、用户目录、会话库、API 和审计系统的职责，再讲清一次首次登录，以及第二个应用如何复用中心会话。

对现代 Web 场景，可以提出 OIDC 授权码加 PKCE、后端持有令牌、浏览器使用本地会话。对企业集成补充 SAML 支持，对已有环境保留 CAS 或 Kerberos 桥接能力。

13.3 再讲安全、状态和取舍

覆盖回调绑定、严格令牌校验、权限和租户隔离。说明中心会话、本地会话、API Token 各有有效期，以及本地退出和全局退出的差别。

针对即时撤销，给出查询状态、事件通知或短寿命令牌的组合，并说明缓存窗口。针对扩展性，说明多实例共享会话、密钥轮换与协议端点容量。

13.4 可直接练习的两分钟回答

我会先确认应用类型、用户来源、租户隔离和退出要求。对于有后端的 Web 系统，采用统一认证中心，各应用作为 OIDC 客户端，使用授权码加 PKCE。企业客户已有 SAML 平台时，通过联合登录或身份代理接入。

用户访问 OA 时，如果本地没有会话，OA 创建绑定浏览器的一次性登录事务，再跳转认证中心。认证中心完成认证后返回授权码。OA 后端换取令牌，通过成熟库检查签名、issuer、audience、有效期和 nonce，映射内部用户，再创建本地 Session。

用户访问 CRM 时仍会跳转认证中心，但浏览器会带认证中心自己的 Cookie，因此通常无需再次输入密码。CRM 拿到自己的认证结果并建立本地会话。各应用和 API 继续检查角色、租户与资源权限。

会话和令牌分别管理有效期。退出 OA 默认只结束本地会话；需要全局退出时，使用平台支持的退出协议并处理通知失败。要求快速封禁时，组合会话失效、状态查询或版本检查，明确缓存延迟。部署上考虑认证中心和会话库高可用、公钥轮换、审计，以及限速和可观测性。

这段回答需要根据真实经验调整。没有做过的协议和功能，可以说设计思路，不要描述成自己已经上线验证过的项目。

14. 高频面试问答

Q1：单点登录的本质是什么？

多个应用信任统一认证中心的认证结果，并复用中心登录状态，减少用户重复认证。业务应用通常各自建立会话，并负责自己的业务权限。

追问时说明跨域靠协议跳转与结果验证，通常不靠所有应用共享同一个 Cookie。

Q2：统一用户库和 SSO 有什么区别？

统一用户库解决账号来源一致；SSO 解决认证结果和登录状态如何被多个应用复用。可以使用同一用户库却每个应用都要求登录。

Q3：认证与授权为什么要分开？

认证确认主体身份，授权判断某个主体能否对某项资源执行某个动作。身份可信不等于有操作权限，尤其不能替代资源归属和租户检查。

Q4：OAuth 2.0 为什么不能直接等同于登录协议？

它的核心是委托授权，Access Token 面向资源访问。OIDC 规定了 ID Token、身份声明及其验证方式，使客户端能标准化确认用户身份。平台自定义的 OAuth 登录还依赖其额外约定。

Q5：SAML 与 OIDC 怎么选？

先看对接生态和双方支持。SAML 常见于企业 Web SSO，XML 签名和 metadata 对接较重；OIDC 适合现代 Web、移动端及 API 生态。不能简单声称 SAML 已淘汰，或 OIDC 在任何场景都更安全。

Q6：用了 JWT 就不用 Session、Redis 和数据库了吗？

JWT 可以减少逐请求查询会话的需要，但刷新、撤销、账号状态、权限和密钥仍需要管理。系统是否需要 Redis 取决于架构，和是否采用 JWT 没有必然对应关系。

Q7：JWT 怎么主动失效？

采用短有效期限制最长存活时间，或者增加撤销列表、会话版本、introspection 等机制。要即时撤销通常需要某种最新状态检查，同时考虑缓存与可用性成本。

Q8：JWT 验签通过为什么还不能直接放行？

还要检查签发者、受众、时间、令牌用途及适用协议约束，再执行权限和资源归属判断。一份发给测试环境或另一 API 的有效签名令牌，也可能不应被当前接口接受。

Q9：为什么授权码要一次性，还要 PKCE？

一次性限制重复使用，PKCE 将兑换绑定到原始事务持有的 verifier。攻击者即使先拿到码，也不应在缺少 verifier 时兑换成功。机密客户端还需要适用的客户端认证。

Q10：state、nonce、PKCE 是不是三个随机数？

它们有不同的协议职责。state 关联请求与回调，nonce 关联认证请求与 ID Token，PKCE 通过 challenge/verifier 关联授权请求与兑换。必须绑定当前事务并正确检查；仅生成随机值却不验证没有作用。

Q11：HttpOnly 是否能防住 XSS？

它能限制脚本直接读取 Cookie，不能阻止恶意脚本在当前站点执行，也不能阻止其利用会话发起请求。仍需防 XSS 和检查敏感操作。

Q12：为什么 Cookie 登录更容易涉及 CSRF？

浏览器会按 Cookie 规则自动附带凭据，攻击者可能诱导用户浏览器提交请求。应用要验证请求意图和来源。由脚本显式设置 Authorization 头的请求，一般不具有完全相同的经典 CSRF 条件，但依然面临 XSS、CORS 配错及其他攻击。

Q13：退出登录为什么比登录复杂？

登录通常是在一条链路上建立状态；退出可能涉及中心会话、多个本地会话、刷新令牌和 API Token。各方可用性不同，通知可能失败，所以要定义范围、幂等处理和收敛时限。

Q14：认证中心挂了，所有系统就都不能用了？

不一定。新登录通常受影响，但有效本地会话或离线可验证令牌可能继续工作。若每次请求都做实时状态查询，受影响范围会扩大。答案取决于校验策略，不能只回答“会”或“不会”。

Q15：网关鉴权后，业务服务还要鉴权吗？

仍需明确业务服务的信任边界，并检查资源级权限。网关负责的统一校验可以减少重复，但身份头要防伪造，内部调用要受保护，不能因为来自内网就放行。

Q16：如何防止不同租户数据串用？

从可信会话中获得用户与租户上下文，校验成员关系，查询和更新都加入租户与资源权限约束。禁止仅凭请求参数里的 tenantId 决定权限，还要关注后台任务、缓存键和跨服务传递。

Q17：一个用户多个设备登录如何管理？

为不同登录会话保存可独立撤销的记录，关联认证中心会话和刷新令牌。支持退出当前设备或全部设备，明确其对浏览器会话与 API Token 的影响。IP 地址只能作为辅助风险信号，不能可靠代表一台设备。

Q18：为什么不能直接拿邮箱做联合身份主键？

邮箱可变更、回收，也可能由不可信提供方声称。通常使用 issuer 与 subject 作为外部身份键，再通过受控过程绑定内部用户。跨提供方账号合并需要额外验证。

Q19：单点登录与单点故障有什么关系？

统一认证提高了控制能力，也集中了承载和安全风险。需要高可用、容量规划与密钥保护，同时让已有业务会话在符合策略的情况下合理持续。SSO 的“单点”指一次登录，不要求物理上只有一台服务器。

Q20：如何证明这套设计安全可用？

不仅测试登录成功，还要测试篡改 state、错误 nonce、错误 verifier、回调重放、错误受众、权限不足、租户切换、会话过期、退出失败和密钥轮换。把观察到的结果与预期策略逐项对应，并保留不含秘密的审计信息。

15. 复习速记与自测

15.1 面试前先记住这些句子

  • SSO 是多应用复用认证的能力，OIDC、SAML、CAS 是常见实现协议。
  • AuthN 验证身份，AuthZ 决定资源操作权限。
  • 跨域 SSO 通常使用跳转和可验证结果，各应用保有自己的会话。
  • OAuth 2.0 主要处理授权，OIDC 增加标准化认证层。
  • ID Token 给客户端确认认证结果，Access Token 给 API，Refresh Token 给授权服务器续期。
  • Cookie 是浏览器机制，Session 是状态机制，JWT 是声明格式。
  • 签名不提供保密性，解码不等于验签，验签不等于授权。
  • 授权码加 PKCE 是现代接入的重要起点，客户端秘密不能放在前端。
  • 本地退出、中心退出、全局退出与令牌撤销需要分别设计。
  • JWT 的离线校验和即时撤销存在状态与延迟取舍。
  • 统一认证之后，业务服务仍要检查租户、角色和资源归属。
  • 离职停用还涉及账号配置、已有会话、API Key 和后台任务。

15.2 不看前文能否回答

  1. 为什么用户在 OA 登录后，CRM 仍要跳转认证中心？
  2. 中心 Cookie 是怎样在跨域登录时发挥作用的？
  3. 如果 API 只验 JWT 签名、不检查 aud，会怎样？
  4. 如果登录后没有更换 Session ID，会有哪些风险？
  5. 为什么 MFA 不能代替 CSRF 和权限检查？
  6. 如何保证停用账号在约定时间内不能继续访问敏感接口？
  7. 同一个 Refresh Token 被多个请求同时使用，会发生什么？
  8. 为什么邮箱相同不能自动认定是同一个用户？
  9. SAML POST 回调丢 Cookie 时，你会按什么顺序排查？
  10. 如果不能依赖第三方 Cookie，SSO 流程如何继续工作？

回答时尽量说出流程、状态、信任边界和取舍，而不是只报协议名称。

16. 动手实验

下面是建议练习，本文没有实际搭建或运行这些系统。

实验一：观察两应用 SSO

准备一个支持 OIDC 的身份平台和两个使用成熟 OIDC 中间件的应用。分别注册不同 client ID 和精确回调地址，两个应用不要共享业务 Session Cookie。

  1. 使用一个全新的浏览器会话，打开 OA。
  2. 观察跳转认证中心、完成认证、返回 OA 的请求链。
  3. 打开 CRM，观察是否仍有协议跳转，以及是否无需再次输密码。
  4. 对照两个应用和认证中心各自的 Cookie。

预期：中心登录被复用，两个业务应用建立独立会话。优先使用配置了本地 HTTPS 的不同测试站点；localhost 不同端口不隔离 Cookie，不能据此证明跨站 Cookie 隔离。

实验二：验证错误路径

在自己的测试环境逐项改变 state、PKCE verifier、受众和回调参数，重复发送已使用的回调。

预期：验证失败，不创建已认证会话。由哪个组件拒绝可以不同，但不能“先登录成功，再记录警告”。测试结束后恢复正确配置。

实验三：观察退出范围

  1. 同时登录 OA 和 CRM。
  2. 只退出 OA，再次访问 OA 和 CRM。
  3. 结束认证中心会话，再访问已有业务会话。
  4. 开启平台支持的全局退出，再重复测试。

记录不同会话的变化，并说明哪些 Access Token 仍有效。预期结果取决于退出配置与令牌验证策略，不能把“全部立即退出”作为无条件标准答案。

实验四：观察续期与账号禁用

缩短测试 Access Token 有效期，观察自动续期；并发触发多个 API 请求，检查是否会重复刷新。随后禁用测试用户，测量浏览器会话和 API 请求在何时停止成功。

这个实验能直接暴露“中心账号禁用”和“所有已发凭据失效”之间的差距。
